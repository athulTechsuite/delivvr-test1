# Order tracking — read-only order detail page and order UI/UX improvements

## Summary
Riders today land on `/orders` and see a grid of order cards but have no way to drill in to view a single order, and the dashboard shows a hardcoded "24 Packages Delivered" tile that is misleading. This ticket introduces a read-only order detail page at `GET /orders/:id` (with strict tenant isolation), makes every card on `/orders` a clickable link to its detail page, replaces the fake `24` stat with a live `countDeliveredByUserId` value, and aligns the dashboard navbar with the orders-list navbar by adding `My Orders` and `New Order` links. The constraint is that we do not introduce status mutation, real-time tracking, or any cross-user access — this is purely a viewing and UX ticket built on the existing `md-card` + Bootstrap Icons pattern already established in `views/orders-list.ejs`.

## Objective
- Reduce navigation dead-ends: enable 100% of orders shown on `/orders` to be clicked through to a dedicated detail view at `/orders/:id`.
- Replace the hardcoded `24 Packages Delivered` figure on `/dashboard` with a live SQL count of orders where `status = 'delivered'` for the current user, eliminating one source of user-reported data inaccuracy.
- Bring the dashboard navbar to parity with the orders-list navbar by adding `My Orders` and `New Order` entries, removing the navigation inconsistency that forces users to detour through the dashboard "Quick Actions" card.
- Preserve strict tenant isolation: `GET /orders/:id` returns `404` when the order does not exist OR when `order.user_id !== req.user.id`, so users can never enumerate other tenants' orders.

## Business Logic

### Order Detail Access (Tenant Isolation)
- Rule: `GET /orders/:id` requires a valid JWT cookie (uses existing `authenticateToken` middleware).
- Rule: `:id` MUST be a positive integer; non-numeric or non-positive values cause `Order.findById` to reject, which the route catches and renders the 404 view.
- Rule: If `Order.findById(id)` resolves to `undefined`/`null`, respond with HTTP 404 and render `views/404.ejs`.
- Rule: If the order is found but `order.user_id !== req.user.id`, respond with HTTP 404 (NOT 403) — we deliberately do not leak existence of other-tenant order IDs.
- Rule: Authenticated user who owns the order receives HTTP 200 and the rendered detail page.

### Delivered Count Aggregation
- Rule: `Order.countDeliveredByUserId(userId)` returns `COUNT(*)` of rows where `user_id = ?` AND `status = 'delivered'` (matching `ORDER_STATUS.DELIVERED`).
- Rule: Method rejects with `new Error('Invalid userId')` if `userId` is not a positive integer (consistency with sibling methods).
- Rule: On DB error in the dashboard handler, fallback value is `0` (consistent with the existing `activeDeliveriesCount: 0` fallback at line 174).

### Order Card Linking
- Rule: Every `<article class="md-card">` in `orders-list.ejs` is wrapped in `<a href="/orders/<%= order.id %>">` with `text-decoration: none` and the link MUST cover the entire card (the whole card is the click target).
- Rule: The link must have `aria-label="View order <%= order.id %> details"` for screen readers.
- Rule: Hover state visually elevates the card (e.g., increased shadow / `md-elevation-4`) to signal interactivity.

### Navbar Parity (dashboard.ejs)
- Rule: Add `<li>` for `My Orders` (href `/orders`, icon `bi-box-seam`) and `<li>` for `New Order` (href `/orders/new`, icon `bi-plus-circle`) BEFORE the Logout `<li>`.
- Rule: The active page (`/dashboard`) keeps `aria-current="page"` and the `md-navbar-link-active` class; new links do NOT carry that class.

app.get('/orders/:id', authenticateToken, async (req, res) => {
    const rawId = req.params.id;
    const orderId = Number.parseInt(rawId, 10);
    if (!Number.isInteger(orderId) || orderId <= 0 || String(orderId) !== rawId) {
        return res.status(404).render('404');
    }
    try {
        const order = await Order.findById(orderId);
        if (!order || order.user_id !== req.user.id) {
            return res.status(404).render('404');
        }
        return res.render('orders-detail', { user: req.user, order });
    } catch (detailErr) {
        console.error('Error loading order detail:', detailErr);
        return res.status(404).render('404');

## Acceptance Criteria
- [ ] Given an authenticated user who owns order `42`, when they GET `/orders/42`, then the response is HTTP 200 and renders `orders-detail.ejs` with the order's id, status chip, pickup_address, delivery_address, package_description, and created_at.
- [ ] Given an authenticated user who does NOT own order `42`, when they GET `/orders/42`, then the response is HTTP 404 and renders `404.ejs` (no body content reveals the order's existence).
- [ ] Given any authenticated user, when they GET `/orders/999999` (non-existent), then the response is HTTP 404.
- [ ] Given any authenticated user, when they GET `/orders/abc` or `/orders/-1` or `/orders/1.5`, then the response is HTTP 404.
- [ ] Given an unauthenticated visitor, when they GET `/orders/42`, then they are redirected to `/login` (via existing `authenticateToken`).
- [ ] Given the orders-list page with N orders, when the page renders, then every card is wrapped in `<a href="/orders/{id}">` and clicking anywhere on the card navigates to that order's detail page.
- [ ] Given a user with 7 orders in `delivered` status and 3 in other statuses, when they load `/dashboard`, then the "Packages Delivered" tile shows `7` (not `24`).
- [ ] Given a user with 0 delivered orders, when they load `/dashboard`, then the "Packages Delivered" tile shows `0`.
- [ ] Given a transient DB error during dashboard stats load, when the dashboard renders, then `deliveredCount` falls back to `0` and the page still renders successfully.
- [ ] Given the dashboard page loads, when the user inspects the navbar, then `My Orders` (linking to `/orders`) and `New Order` (linking to `/orders/new`) entries appear between `Dashboard` and `Logout`.
- [ ] Given an order with `status = 'delivered'`, when its detail page renders, then the status chip uses class `md-chip-delivered` and label text `"Delivered"`.
- [ ] Given an order with `package_description = null`, when its detail page renders, then the description field shows an em-dash `—` placeholder rather than the literal `null`.

- The `authenticateToken` middleware reliably populates `req.user.id` as a positive integer.
