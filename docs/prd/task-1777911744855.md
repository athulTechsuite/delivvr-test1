# Add RBAC system with admin UI for managing user roles

## Summary

This feature completes the role-based access control (RBAC) system for the Delivvr delivery management app. The infrastructure already exists — the `users` table has a `role TEXT NOT NULL DEFAULT 'user'` column, and `middleware/auth.js` exports both `authenticateToken` (which re-reads role from the DB on every request, never trusting the JWT) and `requireRole(role)` (which renders `views/403.ejs` on mismatch). What is missing is the admin-facing surface: a `GET /admin/users` route to list users, a `POST /admin/users/:id/role` endpoint to reassign roles with a self-demotion guard, the `views/admin-users.ejs` template that mirrors the existing `admin-orders.ejs` material-design style, and conditional admin navigation links in all four authenticated view navbars. No schema migration is required; the first admin is seeded via `node database/seed-admin.js <email>`. The key design constraint is that only the two roles `'user'` and `'admin'` are in scope, and the `db.get` SELECT in the dashboard and profile routes must be amended to include the `role` column so navbar conditionals function correctly.

## Objective

- Deliver a `/admin/users` page that lists every registered user with their current role badge, accessible only to admins, rendered via the existing EJS/Bootstrap-Icons/material-design pattern
- Deliver a `POST /admin/users/:id/role` endpoint that validates the incoming role against the allowlist `['user', 'admin']`, prevents self-demotion, and persists the change to the `users` table
- Surface a conditional admin navigation link in all five authenticated view navbars (`dashboard.ejs`, `orders-list.ejs`, `orders-detail.ejs`, `profile.ejs`, `admin-orders.ejs`) visible only when `user.role === 'admin'`
- Fix the `db.get` SELECT queries in `GET /dashboard` and `GET /profile` to include the `role` column so the `user` object passed to view locals carries the role field required by navbar conditionals

## Business Logic

### Role Allowlist
- Rule: The only accepted values for the `role` field are the string literals `'user'` and `'admin'`. Any `POST /admin/users/:id/role` body where `!['user', 'admin'].includes(req.body.role)` must return HTTP 400 with a JSON error body before any DB write is attempted.

### Self-Demotion Guard
- Rule: If `req.user.id === parseInt(req.params.id, 10)` AND `req.body.role === 'user'`, the endpoint must return HTTP 403 with a descriptive error. This prevents the last admin from removing their own admin access and creating a lockout.

### Role Persistence via Live DB Lookup
- Rule: Role is never stored in or trusted from the JWT payload. On every authenticated request, `authenticateToken` executes `SELECT role FROM users WHERE id = ?` and attaches the result to `req.user`. The `POST /admin/users/:id/role` handler therefore only needs to `UPDATE users SET role = ? WHERE id = ?` — the change takes effect on the user's next request without requiring a re-login.

### Dashboard and Profile Query Fix
- Rule: The `db.get` call in `GET /dashboard` must select `id, name, email, role, created_at`. The `db.get` call in `GET /profile` must select `id, name, email, role, created_at`. Without the `role` field, EJS conditionals like `<% if (user.role === 'admin') { %>` evaluate to `false` for all users and the admin nav link never appears.

### Admin Navigation Visibility
- Rule: The admin navigation `<li>` block must be wrapped in `<% if (user && user.role === 'admin') { %> ... <% } %>`. It must appear in the navbar of every authenticated view: `dashboard.ejs`, `orders-list.ejs`, `orders-detail.ejs`, `profile.ejs`, and `admin-orders.ejs`.

```javascript
app.get('/admin/users', authenticateToken, requireRole('admin'), (req, res) => {
    db.all('SELECT id, name, email, role, created_at FROM users ORDER BY id ASC', [], (err, users) => {
        if (err) {
            console.error('Error loading admin users:', err);
            return res.render('admin-users', { user: req.user, users: [] });
        }
        res.render('admin-users', { user: req.user, users });
    });
});

app.post('/admin/users/:id/role', authenticateToken, requireRole('admin'), (req, res) => {
    const rawId = req.params.id;
    const targetId = parseInt(rawId, 10);

    if (!Number.isInteger(targetId) || targetId <= 0 || String(targetId) !== String(rawId).trim()) {
        return res.status(404).json({ error: 'User not found' });
    }

    const { role } = req.body;
    const validRoles = ['user', 'admin'];
    if (!role || !validRoles.includes(role)) {
        return res.status(400).json({ error: `Invalid role. Must be one of: ${validRoles.join(', ')}` });
    }

    if (req.user.id === targetId && role === 'user') {
        return res.status(403).json({ error: 'You cannot demote yourself. Assign another admin first.' });
    }

    db.get('SELECT id FROM users WHERE id = ?', [targetId], (err, row) => {
        if (err) {
            console.error('DB error checking user existence:', err);
            return res.status(500).json({ error: 'Server error' });
        }
        if (!row) {
            return res.status(404).json({ error: 'User not found' });
        }
        db.run('UPDATE users SET role = ? WHERE id = ?', [role, targetId], (updateErr) => {
            if (updateErr) {
                console.error('Error updating user role:', updateErr);
                return res.status(500).json({ error: 'Failed to update role' });
            }
            res.redirect('/admin/users');
        });
    });
});

app.post('/logout', (req, res) => {
    res.clearCookie('token');
    res.redirect('/');
});
```

## Acceptance Criteria

- [ ] `GET /admin/users` returns HTTP 200 for a user with `role = 'admin'` and renders a table containing all users' id, name, email, role, and member-since date
- [ ] `GET /admin/users` returns HTTP 403 and renders `views/403.ejs` for a user with `role = 'user'`
- [ ] `GET /admin/users` redirects to `/login` when no valid JWT cookie is present
- [ ] `POST /admin/users/:id/role` with `role=admin` in the body updates the target user's row in the `users` table and redirects to `/admin/users`
- [ ] `POST /admin/users/:id/role` with `role=user` targeting a different user successfully demotes that user and redirects to `/admin/users`
- [ ] `POST /admin/users/:id/role` with an unrecognised role value (e.g. `role=superadmin`) returns HTTP 400 without modifying the database
- [ ] `POST /admin/users/:id/role` where `:id` matches the authenticated admin's own id and `role=user` returns HTTP 403 with a descriptive error message
- [ ] `POST /admin/users/:id/role` where `:id` does not match any row in `users` returns HTTP 404
- [ ] `POST /admin/users/:id/role` where `:id` is not a valid positive integer (e.g. `abc`) returns HTTP 404
- [ ] The admin nav link `<a href="/admin/users">` is present and visible in `dashboard.ejs`, `orders-list.ejs`, `orders-detail.ejs`, `profile.ejs`, and `admin-orders.ejs` when authenticated as an admin
- [ ] The admin nav link is absent from the rendered HTML in all views when authenticated as a regular user
- [ ] `GET /dashboard` passes a `user` object with `role` set to the view locals so the navbar conditional evaluates correctly
- [ ] `GET /profile` passes a `user` object with both `id` and `role` set to the view locals
- [ ] Existing `GET /admin/orders` continues to return HTTP 403 for non-admin users
- [ ] Existing `PATCH /orders/:id/status` continues to return HTTP 403 for non-admin users

**Risk Level:** LOW

**Deployment Order:**
1. No database migration needed — `users.role` column exists in both development and production schemas
2. Deploy updated `app.js` (new routes + fixed `db.get` SELECT queries)
3. Deploy new `views/admin-users.ejs`

**Rollback Plan:**
1. Revert the feature branch commit — this removes both new routes from `app.js`, the `admin-users.ejs` view, and all navbar additions in a single git revert
2. The `db.get` SELECT query change adds non-breaking columns (`role`, `id`) to the result set; reverting to the narrower SELECT is safe and has no schema impact

- No npm packages required: confirmed — `db.all` and `db.run` are already available on the existing `sqlite3` instance in `app.js`

## Scope Boundaries

**In Scope:**
- `GET /admin/users` route and `views/admin-users.ejs` template
- `POST /admin/users/:id/role` endpoint with role validation and self-demotion guard
- Conditional admin navigation link in `dashboard.ejs`, `orders-list.ejs`, `orders-detail.ejs`, `profile.ejs`, `admin-orders.ejs`
- Fixing `db.get` SELECT queries in `GET /dashboard` and `GET /profile` to include `role` (and `id` for profile)
- Roles `'user'` and `'admin'` only

**Out of Scope:**
- Roles beyond `'user'` and `'admin'` (e.g. driver, dispatcher, moderator)
- Bulk role assignment (selecting multiple users at once)
- User deletion from the admin UI
- Audit log of role changes
- Email notifications when a user's role changes
- REST/JSON API for role management (the endpoint returns JSON errors but redirects on success — it is not a standalone JSON API)
- New npm packages
- Password reset or account suspension features
- Pagination of the `/admin/users` table

**Assumptions:**
- The `users.role` column already exists with `DEFAULT 'user'` in both the development SQLite file and any production DB
- At least one admin account is seeded before the feature goes live (`node database/seed-admin.js <email>`)
- Only two roles are needed for the foreseeable future — adding a third role would require schema-level decisions outside this spec
- The app continues to use server-side EJS rendering; no React/Vue/SPA changes are in scope
- `express-validator` is already installed (used in existing routes) and available for any additional input validation if needed
