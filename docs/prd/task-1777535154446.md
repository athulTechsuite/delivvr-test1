# Add role-based access control (admin/customer) to delivery app

## Summary
This feature introduces a two-role RBAC system — `admin` and `customer` — to the Node.js/Express delivery management app. All new user registrations default to the `customer` role. The `admin` role unlocks a new `/admin/users` page where admins can view every registered user and promote or demote their role. A new `requireRole` middleware enforces per-route access and renders a proper `403.ejs` page on denial, consistent with the existing `404.ejs` error-handling convention. The key architectural constraint is that roles are stored in the JWT at login time, so role changes do not propagate to existing sessions — a deliberate v1 trade-off documented explicitly.

## Objective
- Add `role TEXT NOT NULL DEFAULT 'customer'` to the `users` table via a safe, idempotent `ALTER TABLE` migration and embed the role in every JWT so downstream middleware can enforce access without a DB round-trip on each request.
- Implement a `requireRole(...allowedRoles)` middleware factory that reads `req.user.role` and renders HTTP 403 on denial, enabling declarative per-route access control consistent with the existing `authenticateToken` pattern.
- Deliver `/admin/users` (GET) and `/admin/users/:id/role` (POST) routes with a server-rendered EJS view, giving admins full visibility and control over user roles without any additional infrastructure.

## Business Logic

### Role Enumeration
- Rule: Exactly two roles are valid — `'customer'` (default) and `'admin'`. No other value may be stored or accepted. The POST /admin/users/:id/role handler must validate that the submitted `role` value is one of these two strings before executing the UPDATE.
- Rule: The `users` table column is `role TEXT NOT NULL DEFAULT 'customer'`. Existing rows receive `'customer'` automatically via the SQLite column default at migration time.

### JWT Payload
- Rule: At `POST /login`, after password verification, `jwt.sign` must include `{ id: user.id, email: user.email, role: user.role }` with `expiresIn: '24h'` (unchanged). The `role` field is read from the DB row; it is never taken from user-supplied input.
- Rule: A user's active JWT continues to reflect the role at login time. Promoting a user from `customer` to `admin` via `/admin/users/:id/role` takes effect only on the user's next login. This is accepted v1 behaviour.

### Route Access Matrix
- Rule: `GET /orders/new` and `POST /orders` — `requireRole('customer', 'admin')` — both roles may place orders.
- Rule: `GET /admin/users` — `requireRole('admin')` — admin-only user list view.
- Rule: `POST /admin/users/:id/role` — `requireRole('admin')` — admin-only role mutation.
- Rule: `authenticateToken` always runs before `requireRole` in every middleware chain; an unauthenticated request redirects to `/login` before the role check is ever evaluated.

### First-Admin Bootstrap
- Rule: Because `POST /signup` always creates a `customer`, the first admin must be bootstrapped via a direct SQL update: `UPDATE users SET role='admin' WHERE email='admin@example.com';`. This must be documented in the project README. No automated seed script is in scope.

### SQLite Migration Safety
- Rule: `ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'customer'` is executed inside `db.serialize()` in `app.js`. The error callback must check `err && err.message && err.message.includes('duplicate column name')` and silently return; all other errors must be logged as fatal so regressions are visible.

const authenticateToken = (req, res, next) => {
    const token = req.cookies.token;

    }
    
    jwt.verify(token, JWT_SECRET, (err, user) => {

    });

**After:**
```javascript
// Authentication middleware
const authenticateToken = (req, res, next) => {
    const token = req.cookies.token;
    
    if (!token) {
        return res.redirect('/login');
    }
    
    jwt.verify(token, JWT_SECRET, (err, user) => {
        if (err) {
            return res.redirect('/login');
        }
        req.user = user;
        next();
    });
};

// Role-based access control middleware factory
const requireRole = (...allowedRoles) => (req, res, next) => {
    if (!req.user || !allowedRoles.includes(req.user.role)) {
        return res.status(403).render('403');
    }
    next();
};
```

### Admin Routes
**Files:** `app.js`
**What:** Add two new routes before the existing `POST /logout` route. The GET lists all users via inline `db.all`; the POST validates the submitted role, updates the DB, and redirects.

**Before (key section):**
```javascript
app.post('/logout', (req, res) => {
    res.clearCookie('token');
    res.redirect('/');
});
```

**After:**
```javascript
// Admin: user management
app.get('/admin/users', authenticateToken, requireRole('admin'), (req, res) => {
    db.all('SELECT id, name, email, role, created_at FROM users ORDER BY created_at ASC', (err, users) => {
        if (err) {
            console.error('Database error loading admin user list:', err);
            return res.status(500).send('Unable to load users.');
        }
        res.render('admin-users', { user: req.user, users });
    });
});

app.post('/admin/users/:id/role', authenticateToken, requireRole('admin'), (req, res) => {
    const rawId = req.params.id;
    const parsedId = Number.parseInt(rawId, 10);
    const VALID_ROLES = ['customer', 'admin'];
    const newRole = req.body.role;

    if (!Number.isInteger(parsedId) || parsedId <= 0) {
        return res.status(400).send('Invalid user ID.');
    }
    if (!VALID_ROLES.includes(newRole)) {
        return res.status(400).send('Invalid role value.');
    }

    db.run('UPDATE users SET role = ? WHERE id = ?', [newRole, parsedId], function (err) {
        if (err) {
            console.error('Database error updating user role:', err);
            return res.status(500).send('Unable to update role.');
        }
        res.redirect('/admin/users');
    });
});

app.post('/logout', (req, res) => {
    res.clearCookie('token');
    res.redirect('/');
});
```

## Acceptance Criteria
- [ ] Given an unauthenticated request, when `GET /orders/new` is hit, then the response is a `302` redirect to `/login` (authenticateToken fires first)
- [ ] Given a logged-in `customer`, when `GET /orders/new` is requested, then the response is `200` with the order form rendered
- [ ] Given a logged-in `admin`, when `GET /orders/new` is requested, then the response is `200` with the order form rendered
- [ ] Given a logged-in `customer`, when `GET /admin/users` is requested, then the response is `403` with `views/403.ejs` rendered (contains "Access Denied" heading)
- [ ] Given a logged-in `admin`, when `GET /admin/users` is requested, then the response is `200` with a table showing every user's `id`, `name`, `email`, `role`, and `created_at`
- [ ] Given a logged-in `admin`, when `POST /admin/users/:id/role` is submitted with `role=admin`, then the DB row is updated and the response is a `302` redirect to `/admin/users`
- [ ] Given a logged-in `admin`, when `POST /admin/users/:id/role` is submitted with `role=superuser`, then the response is `400` (invalid role value rejected)
- [ ] Given a successful `POST /login`, the response JWT payload includes the `role` field for both `customer` and `admin` accounts
- [ ] Given an existing user row with no `role` column before migration, when the server starts, then `SELECT role FROM users` returns `'customer'` for that row
- [ ] Given the server is restarted after the migration has already run, when the `ALTER TABLE` executes again, then the server starts without crashing
- [ ] Given `views/403.ejs` is rendered, the HTTP status code is `403` and the page contains a "Back to Dashboard" link pointing to `/dashboard`
- [ ] Given `models/User.js` `findAll()` is called, each returned row includes the `role` field with a valid value

- **TC-F-002** Customer blocked from admin page: Login as customer → `GET /admin/users` → expect `403`, response body contains "Access Denied"
- **TC-F-003** Admin can access order form: Bootstrap admin via SQL → login → `GET /orders/new` → expect `200`, form renders normally
- **TC-F-004** Admin can view user list: Login as admin → `GET /admin/users` → expect `200`, response body contains a `<table>` with at least one row per registered user
- **TC-F-005** Admin promotes user: Login as admin → `POST /admin/users/2/role` body `role=admin` → expect `302` to `/admin/users` → `SELECT role FROM users WHERE id=2` returns `'admin'`
- **TC-F-006** Admin demotes user: Login as admin → `POST /admin/users/2/role` body `role=customer` → expect `302` → DB confirms `role='customer'`
- **TC-F-007** New signup defaults to customer: `POST /signup` with valid body → `SELECT role FROM users WHERE email=?` returns `'customer'`
- **TC-F-008** JWT contains role: `POST /login` → decode returned `token` cookie → JWT payload has `{ id, email, role }` with `role` equal to DB value

### Edge Cases (TC-E-XXX)
- **TC-E-001** Role change JWT lag: Admin promotes user B → user B's existing session token still carries `role='customer'` → `GET /admin/users` with that token → `403` (role resolves at next login only)
- **TC-E-002** Invalid role value rejected: `POST /admin/users/1/role` with `role=superuser` → `400` response, no DB update
- **TC-E-003** Non-integer user ID rejected: `POST /admin/users/abc/role` → `400` response
- **TC-E-004** Server restart idempotency: Run `ALTER TABLE` twice (simulated by restarting dev server) → no `FATAL` log, server binds to port successfully, all existing data intact
- **TC-E-005** Unauthenticated admin route: `GET /admin/users` with no cookie → `302` to `/login` (authenticateToken fires before requireRole — role check is never reached)

### Regression (TC-R-XXX)
- **TC-R-001** Unauthenticated order creation blocked: No `token` cookie → `POST /orders` → `302` to `/login` (existing `authenticateToken` behaviour preserved; `requireRole` is never reached)
- **TC-R-002** Tenant order isolation preserved: Customer A logged in → `GET /orders/:id` for an order owned by customer B → `404` (not `403`) — existing isolation logic in `app.js` lines 380–383 must not be touched
- **TC-R-003** Existing signup flow unaffected: `POST /signup` with valid inputs → `302` redirect to `/login`, no role field in the body required, user created with `role='customer'` in DB

**Key Risks:**
- **JWT role staleness (MEDIUM):** Role changes don't propagate to existing 24 h sessions. Mitigation: document clearly in README; for v1 the 24 h TTL is the natural refresh window. Future mitigation: short-lived tokens or a token denylist.
- **`models/User.js` DB path mismatch (HIGH before fix):** The current file points to `database.db` which doesn't exist in production. If the admin route calls `User.findAll()` before the path is fixed, it will query an empty database. Mitigation: fix the path in the same PR; use inline `db.all` in the admin route as the primary query (removing the dependency on `models/User.js` for the route itself).
- **SQLite `ALTER TABLE` no `IF NOT EXISTS` for columns (LOW):** Without the duplicate-column error check, server restarts would crash. Mitigation: the error callback in the migration explicitly checks for `'duplicate column name'` in the error message.

## Scope Boundaries
**In Scope:**
- Add `role TEXT NOT NULL DEFAULT 'customer'` column to `users` table via idempotent ALTER TABLE migration in `app.js`
- Embed `role` in JWT payload at `POST /login`
- `requireRole(...allowedRoles)` middleware factory in `app.js`
- `views/403.ejs` — new file modelled on `views/404.ejs`
- Restrict `GET /orders/new` and `POST /orders` to `requireRole('customer', 'admin')`
- `GET /admin/users` — lists all users with roles; admin-only
- `POST /admin/users/:id/role` — updates user role; admin-only
- `views/admin-users.ejs` — server-rendered table with per-row role-change form
- Fix `models/User.js` DB path (`database.db` → `database.sqlite`) and add `role` to `findAll()` SELECT

**Out of Scope:**
- Driver role and delivery-status update route (no driver role in design, no status-update route exists)
- Signup-time role selection (all new users are always `customer`)
- Session invalidation or JWT revocation on role change
- Pagination, filtering, or search on `/admin/users`
- Audit logging of role changes
- Rate limiting on admin endpoints

**Assumptions:**
- The canonical database file is `database.sqlite` in the project root, as used by `app.js` (line 21) and `models/Order.js` (line 20)
- The first admin account is bootstrapped manually via direct SQL; no automated seed script is required
- Admin users may change any user's role including their own (no self-demotion guard)
- The `/admin/users` page uses server-rendered EJS, consistent with every other view in the application
- The `DB_PATH` environment variable, when set, takes precedence over the hardcoded default path in both `app.js` and `models/User.js`
