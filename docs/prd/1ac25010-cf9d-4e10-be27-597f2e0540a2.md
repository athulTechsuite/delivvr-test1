# Build Full-Stack Food Delivery App with Role-Based Dashboards

## Summary

Build a production-ready, full-stack online food delivery application from scratch on top of the existing Delivvr repository. The new application uses Next.js 14+ App Router for both frontend pages and backend API Route Handlers, replacing the current Express/EJS/SQLite stack for this feature surface. Three distinct user roles — Customer, Restaurant, and Delivery Agent — each receive a dedicated login page and a role-specific dashboard. Authentication is implemented via custom JWT tokens (using the `jose` library for Edge-compatible signing/verification) stored in httpOnly cookies, with a Next.js middleware file guarding all protected routes. The PostgreSQL database is managed exclusively through Prisma ORM, with a schema covering Users (with role), Restaurants, MenuItems, Orders, and OrderItems. React Query handles all client-side data fetching and cache invalidation. Tailwind CSS provides the styling layer. The existing Express app continues to run independently; this PRD describes only the new Next.js application living in a `/app` directory structure.

## Objective

- Customers can browse all active restaurants, view their menus, place orders, and track order status in real time through a polling-based dashboard — measurable by a complete order lifecycle from `PENDING` through `DELIVERED` in the database.
- Restaurants can create, update, and delete menu items and transition incoming orders through the status workflow (`PENDING` → `CONFIRMED` → `PREPARING` → `READY_FOR_PICKUP`), measurable by the restaurant dashboard reflecting only their own orders and items.
- Delivery Agents can view only the orders assigned to them and advance delivery status (`READY_FOR_PICKUP` → `OUT_FOR_DELIVERY` → `DELIVERED`), measurable by the order record's `agentId` foreign key being set and `status` advancing correctly.
- JWT-based authentication gates every dashboard and API route, with httpOnly cookie storage and live DB role lookup on every request — measurable by a token carrying role `CUSTOMER` being rejected with HTTP 401 when calling a restaurant-only endpoint.

## Business Logic

### User Roles and Allowed Actions
- **Rule:** Exactly three role values exist: `CUSTOMER`, `RESTAURANT`, `AGENT`. These are a Prisma enum stored in the `users` table. No other role is valid; any attempt to register with a different role returns HTTP 400.
- **Rule:** Role is determined at registration time by which login page the user comes from (`/login/customer`, `/login/restaurant`, `/login/agent`). Role is never user-editable after account creation.
- **Rule:** Role is never trusted from the JWT payload. Every authenticated API route handler reads `SELECT role FROM users WHERE id = ?` (via Prisma `findUnique`) and rejects if role does not match the required role for that endpoint.

### Authentication Flow
- **Rule:** POST `/api/auth/login` accepts `{ email, password, role }`. Password is compared with bcrypt (12 salt rounds). On success, a `jose` HS256 JWT is minted with payload `{ sub: userId, email, role }` and 24-hour expiry. The token is written to an httpOnly, Secure (in production), SameSite=Lax cookie named `delivvr_token`. Response body returns `{ ok: true, role }`.
- **Rule:** POST `/api/auth/register` accepts `{ name, email, password, role }`. Name 2–50 chars, letters and spaces only. Email unique per Prisma constraint. Password 8–128 chars, must contain at least one lowercase, one uppercase, one digit. Returns HTTP 201 on success, HTTP 409 if email already taken, HTTP 400 on validation failure.
- **Rule:** POST `/api/auth/logout` clears the `delivvr_token` cookie by setting `Max-Age=0`. Returns HTTP 200 `{ ok: true }`.
- **Rule:** The Next.js `middleware.ts` file (at repo root, matcher covering `/dashboard/**` and `/api/**` except `/api/auth/**`) reads the cookie, verifies the JWT with `jose`, does a live Prisma role lookup, and attaches `{ userId, email, role }` to request headers as `x-user-id`, `x-user-email`, `x-user-role`. Expired or invalid tokens redirect browser requests to the appropriate role login page and return HTTP 401 for API requests.

### Order Status Transitions
- **Rule:** Valid statuses (Prisma enum `OrderStatus`): `PENDING`, `CONFIRMED`, `PREPARING`, `READY_FOR_PICKUP`, `OUT_FOR_DELIVERY`, `DELIVERED`, `CANCELLED`.
- **Rule:** Customers may only cancel (`PENDING` → `CANCELLED`). They cannot advance any other status.
- **Rule:** Restaurants may transition: `PENDING` → `CONFIRMED`, `CONFIRMED` → `PREPARING`, `PREPARING` → `READY_FOR_PICKUP`. Restaurants may also cancel (`PENDING` → `CANCELLED` or `CONFIRMED` → `CANCELLED`). No other restaurant-initiated transitions are valid; attempts return HTTP 422.
- **Rule:** Delivery agents may transition: `READY_FOR_PICKUP` → `OUT_FOR_DELIVERY`, `OUT_FOR_DELIVERY` → `DELIVERED`. Agent must be the assigned agent (`orders.agentId === req.userId`); if not assigned, return HTTP 403.
- **Rule:** An order cannot be modified once it is `DELIVERED` or `CANCELLED`. Attempts return HTTP 422.

### Restaurant Scoping
- **Rule:** A `Restaurant` row is created automatically when a user with role `RESTAURANT` first completes registration. The `Restaurant.ownerId` foreign key links the two. One user maps to at most one restaurant.
- **Rule:** All restaurant dashboard endpoints filter by `restaurantId` derived from `req.userId` via `Restaurant.findUnique({ where: { ownerId: userId } })`. A restaurant user may not access another restaurant's orders or menu items; attempts return HTTP 403.

### Menu Items
- **Rule:** Menu items have `name` (1–100 chars), `description` (optional, max 500 chars), `price` (positive decimal, max 2 decimal places, max value 9999.99), `available` (boolean, default `true`), and `restaurantId` foreign key.
- **Rule:** Customers only see menu items where `available = true` and the parent restaurant's `isActive = true`. Restaurants can see all their own menu items regardless of `available` flag.

### Order Placement
- **Rule:** POST `/api/orders` (Customer only). Body: `{ restaurantId, items: [{ menuItemId, quantity }], deliveryAddress }`. Each `quantity` must be a positive integer ≥ 1. `deliveryAddress` is required, 5–500 chars. Restaurant must be active; menu items must belong to the given restaurant and be available. If any item fails these checks, the entire order is rejected with HTTP 422 listing which item IDs are invalid.
- **Rule:** An `Order` record and one `OrderItem` record per line are written in a single Prisma transaction. No partial inserts.

### Delivery Agent Assignment
- **Rule:** Agent assignment is performed by the restaurant: PATCH `/api/orders/:id/assign` accepts `{ agentId }` and sets `orders.agentId`. Agent must have role `AGENT`; otherwise HTTP 422.
- **Rule:** An agent's dashboard lists only orders where `orders.agentId = req.userId` and `status IN (READY_FOR_PICKUP, OUT_FOR_DELIVERY)`.

### 2. Next.js Middleware (New File)

**Files:** `src/middleware.ts`

**What:** Edge-compatible JWT verification using `jose`. Reads `delivvr_token` cookie, verifies HS256 signature, does a Prisma role lookup, then injects `x-user-id`, `x-user-email`, `x-user-role` headers for downstream Route Handlers. On failure, redirects browser requests to the correct login page and returns 401 for API requests.

**Before (key section):**
```typescript
// File does not exist
// Pattern derived from existing middleware/auth.js:
//   jwt.verify(finalToken, jwtSecret, (err, decoded) => {
//     db.get('SELECT role FROM users WHERE id = ?', [decoded.id], ...)
//   })
```

**After:**
```typescript
import { NextRequest, NextResponse } from 'next/server'
import { jwtVerify } from 'jose'

const PUBLIC_PATHS = ['/login', '/api/auth']
const JWT_SECRET = new TextEncoder().encode(process.env.JWT_SECRET!)

export async function middleware(req: NextRequest) {
  const { pathname } = req.nextUrl
  if (PUBLIC_PATHS.some((p) => pathname.startsWith(p))) return NextResponse.next()

  const token = req.cookies.get('delivvr_token')?.value
  if (!token) return redirectOrUnauthorized(req)

  try {
    const { payload } = await jwtVerify(token, JWT_SECRET)
    const res = NextResponse.next()
    res.headers.set('x-user-id', payload.sub as string)
    res.headers.set('x-user-email', payload.email as string)
    res.headers.set('x-user-role', payload.role as string)
    return res
  } catch {
    return redirectOrUnauthorized(req)
  }
}

function redirectOrUnauthorized(req: NextRequest) {
  if (req.nextUrl.pathname.startsWith('/api/')) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }
  return NextResponse.redirect(new URL('/login/customer', req.url))
}

export const config = {
  matcher: ['/dashboard/:path*', '/api/:path*'],
}
```

```typescript
// src/app/api/auth/login/route.ts
import { SignJWT } from 'jose'
import { cookies } from 'next/headers'
import { prisma } from '@/lib/prisma'
import bcrypt from 'bcrypt'

export async function POST(req: Request) {
  const { email, password, role } = await req.json()
  const user = await prisma.user.findUnique({ where: { email } })
  if (!user || user.role !== role) {
    return Response.json({ error: 'Invalid credentials' }, { status: 401 })
  }
  const match = await bcrypt.compare(password, user.passwordHash)
  if (!match) return Response.json({ error: 'Invalid credentials' }, { status: 401 })

  const secret = new TextEncoder().encode(process.env.JWT_SECRET!)
  const token = await new SignJWT({ sub: user.id, email: user.email, role: user.role })
    .setProtectedHeader({ alg: 'HS256' })
    .setExpirationTime('24h')
    .sign(secret)

  const cookieStore = await cookies()
  cookieStore.set('delivvr_token', token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    maxAge: 86400,
    path: '/',
  })
  return Response.json({ ok: true, role: user.role }, { status: 200 })
}
```

```typescript
import { headers } from 'next/headers'

export async function requireRole(role: string): Promise<{ userId: string } | Response> {
  const h = await headers()
  const userRole = h.get('x-user-role')
  const userId = h.get('x-user-id')
  if (userRole !== role || !userId) {
    return Response.json({ error: 'Forbidden' }, { status: 403 }) as unknown as Response
  }
  return { userId }
}
```

## Acceptance Criteria

- [ ] **Given** an unauthenticated request to `/dashboard/customer`, **when** the middleware runs, **then** the browser is redirected to `/login/customer` and no dashboard content is rendered.
- [ ] **Given** a valid `CUSTOMER` JWT cookie, **when** GET `/api/restaurants` is called, **then** the response is HTTP 200 with a JSON array of restaurants where `isActive = true`.
- [ ] **Given** a valid `CUSTOMER` JWT cookie, **when** GET `/api/restaurants/:id/menu` is called for an active restaurant, **then** only menu items with `available = true` are returned.
- [ ] **Given** a valid `CUSTOMER` JWT cookie, **when** POST `/api/orders` is submitted with valid `restaurantId`, `items`, and `deliveryAddress`, **then** one `Order` and N `OrderItem` rows are created in a single transaction and HTTP 201 is returned with the order ID.
- [ ] **Given** an order in `PENDING` status, **when** a `CUSTOMER` sends PATCH `/api/orders/:id/status` with `{ status: "CANCELLED" }`, **then** the order transitions to `CANCELLED` and HTTP 200 is returned.
- [ ] **Given** a `CUSTOMER` JWT token, **when** that token is used against POST `/api/restaurant/menu`, **then** HTTP 403 is returned.
- [ ] **Given** a valid `RESTAURANT` JWT cookie, **when** POST `/api/restaurant/menu` is called with valid `name`, `price`, `available`, **then** a `MenuItem` row is created with `restaurantId` set to the authenticated restaurant and HTTP 201 is returned.
- [ ] **Given** an order in `PENDING` status, **when** the owning restaurant sends PATCH `/api/restaurant/orders/:id/status` with `{ status: "CONFIRMED" }`, **then** the order transitions to `CONFIRMED` and the customer dashboard reflects the new status within the next polling cycle (≤15 seconds).
- [ ] **Given** an order in `READY_FOR_PICKUP` status with `agentId` set, **when** the assigned agent sends PATCH `/api/agent/orders/:id/status` with `{ status: "OUT_FOR_DELIVERY" }`, **then** the order transitions to `OUT_FOR_DELIVERY` and HTTP 200 is returned.
- [ ] **Given** a `RESTAURANT` JWT token, **when** PATCH `/api/agent/orders/:id/status` is called, **then** HTTP 403 is returned.
- [ ] **Given** an order in `DELIVERED` status, **when** any role attempts a status update, **then** HTTP 422 is returned with `{ error: "Order is already finalized" }`.
- [ ] **Given** registration with an email already in the database, **when** POST `/api/auth/register` is called, **then** HTTP 409 is returned with `{ error: "Email already registered" }`.
- [ ] **Given** a password not meeting complexity rules (no uppercase), **when** POST `/api/auth/register` is submitted, **then** HTTP 400 is returned with a message indicating the password requirement.
- [ ] **Given** an expired JWT cookie, **when** any protected API route is called, **then** HTTP 401 is returned with `{ error: "Unauthorized" }`.
- [ ] **Given** a restaurant user who does not yet have a `Restaurant` row, **when** the restaurant dashboard loads, **then** the UI prompts them to complete restaurant profile setup (restaurant name + address) before menu/order management is accessible.

## Risk and Deployment

**Risk Level:** HIGH

**Deployment Order:**
1. Provision PostgreSQL database (separate from the existing SQLite instance).
2. Set `DATABASE_URL`, `JWT_SECRET` (minimum 32 chars, randomly generated), and `NODE_ENV` environment variables.
3. Run `prisma migrate deploy` to apply all migrations to the PostgreSQL database.
4. Run `prisma generate` to generate the Prisma Client.
5. Deploy the Next.js application (`next build && next start`).
6. Verify the Express app continues to run on its existing port; the Next.js app runs on port 3001 (or behind a reverse proxy).
7. Smoke-test all three login flows and role-specific dashboard loads.

**Rollback Plan:** The Next.js application is a standalone deployment and does not share the SQLite database used by the Express app. Rolling back means stopping the Next.js process and reverting DNS/proxy configuration to point solely at the Express app. The Prisma PostgreSQL database can be dropped; it contains no shared data with the Express SQLite DB.

**Key Risks:**
- **JWT_SECRET mismatch between Express and Next.js:** The two apps use different token formats (Express uses `jsonwebtoken` with `{ id, email }` payload; Next.js uses `jose` with `{ sub, email, role }` payload). Tokens are not cross-compatible — this is intentional isolation. Risk: developers may accidentally copy Express tokens into Next.js cookies. Mitigation: use different cookie names (`token` vs `delivvr_token`) and document this separation.
- **Prisma Client cold-start latency in Edge middleware:** Using Prisma in `middleware.ts` is not supported in the Edge runtime. Mitigation: the middleware uses only `jose` for token verification (no Prisma call). Live role lookup happens inside Route Handlers via `requireRole()` utility, which runs in Node.js runtime.
- **Missing `Restaurant` row on first restaurant login:** A restaurant user who has no `Restaurant` row will see an empty dashboard. Mitigation: the dashboard detects the missing row and renders a setup prompt; API routes return HTTP 404 with `{ error: "Restaurant profile not found" }` until setup is complete.
- **Prisma enum migration irreversibility:** Once `OrderStatus` and `Role` enums are applied in PostgreSQL, renaming values requires a multi-step migration. Mitigation: the enum values are final as specified; no aliases or renames are planned.

## Scope Boundaries

**In Scope:**
- Next.js 14+ App Router project structure under `src/app/`
- Three separate login pages and dashboards per role
- Custom JWT authentication via `jose` with httpOnly cookie storage
- PostgreSQL database with Prisma ORM (five tables: User, Restaurant, MenuItem, Order, OrderItem)
- API Route Handlers under `src/app/api/`
- Customer: browse restaurants, browse menus, place orders, track order status (polling every 15 seconds)
- Restaurant: menu item CRUD, view incoming orders, update order status, assign delivery agent
- Delivery Agent: view assigned orders, update delivery status
- Next.js middleware for JWT verification and role injection
- Tailwind CSS styling for all pages
- React Query for client-side data fetching and cache management
- Bcrypt password hashing (12 salt rounds)
- Input validation via Zod on all API routes

**Out of Scope:**
- Payment processing or integration with any payment gateway
- Real-time WebSocket or Server-Sent Events for order updates (polling only)
- Push notifications (mobile or web)
- Email verification or password reset flows
- Admin super-user management interface
- Image upload for restaurant photos or menu items
- Order history beyond basic list view
- Multi-restaurant ordering (one restaurant per order)
- Migrating existing Express/SQLite data to PostgreSQL
- Mobile native application
- Internationalization / localization
- Map-based delivery tracking UI

**Assumptions:**
- A PostgreSQL 14+ instance is available and `DATABASE_URL` is set before running migrations.
- `JWT_SECRET` is a cryptographically random string of at least 32 characters shared between deployments of the Next.js app.
- The Express app and Next.js app run as separate processes and do not share a database; the Express app continues to use SQLite unchanged.
- No existing user accounts from the Express app need to be migrated to the Next.js/PostgreSQL system.
- Delivery agent accounts are created by self-registration on `/login/agent` (register link); there is no admin-controlled provisioning flow in this scope.
- The `jose` library is used instead of `jsonwebtoken` because `jose` is Edge-runtime compatible; `bcrypt` (not `bcryptjs`) is used in Node.js Route Handlers only.
