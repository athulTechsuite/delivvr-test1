# Add role-based access control (RBAC) to delivery management app

## Summary
This feature introduces a 3-role RBAC system (`customer`, `driver`, `admin`) into the Node.js/Express delivery management app. A `role TEXT NOT NULL DEFAULT 'customer'` column is added to the `users` table across all four DDL locations, the role is embedded in the JWT at login so every authenticated request carries the caller's role without a DB round-trip, and a new `authorizeRole(...roles)` middleware gates the existing order routes to `customer`-only access. The key design constraint is that `app.js` defines its own inline `authenticateToken` and must not be touched — `authorizeRole` is imported from `middleware/auth.js` and chained alongside the existing inline function, keeping the consolidation work explicitly out of scope.

## Objective
- Add `role TEXT NOT NULL DEFAULT 'customer'` to the `users` table DDL in all four source files and run an idempotent `ALTER TABLE` migration at startup so existing SQLite databases are upgraded without data loss
- Export `authorizeRole(...roles)` from `middleware/auth.js` that returns HTTP 403 `{ error: 'Forbidden' }` when `req.user.role` is not in the allowed list
- Gate `GET /orders/new`, `POST /orders`, `GET /orders`, and `GET /orders/:id` to the `customer` role so non-customer tokens are explicitly rejected at the middleware layer

## Business Logic
### Role Enumeration
- Rule: Valid role values are exactly the string literals `'customer'`, `'driver'`, and `'admin'` — no other values are accepted or defined
- Rule: All new users receive `role = 'customer'` by default via the column `DEFAULT 'customer'`; no signup-time role selection is supported
- Rule: The `driver` and `admin` roles are defined in the column and carried in the JWT but no routes are gated to them in this task

### authorizeRole Middleware
- Rule: `authorizeRole(...roles)` returns a `(req, res, next)` middleware function; the roles list is provided at route-definition time (e.g. `authorizeRole('customer')`)
- Rule: If `req.user.role` is present in the `roles` array, the middleware calls `next()`; otherwise it returns `res.status(403).json({ error: 'Forbidden' })` immediately — no redirect
- Rule: The 403 JSON shape `{ error: 'Forbidden' }` is consistent with the existing 500 JSON shape `{ error: 'Server configuration error' }` already used in `middleware/auth.js`

### JWT Payload
- Rule: `app.js` `POST /login` (line 285) signs `{ id: user.id, email: user.email }` — `role: user.role` must be added as a third field; the key name `id` must remain unchanged
- Rule: `routes/auth.js` `POST /login` (line 100) signs `{ userId: user.id, email: user.email }` — `role: user.role` must be added as a third field; the key name `userId` must remain unchanged
- Rule: `authorizeRole` reads only `req.user.role`, which is consistent regardless of which login path generated the token

### Database Migration
- Rule: `ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'customer'` must be wrapped in a try/catch (or error-ignored `.run()`) because SQLite does not support `IF NOT EXISTS` on `ALTER TABLE`; a duplicate-column error on subsequent startups must be silently ignored, not re-thrown
- Rule: The migration must run inside the existing `db.serialize()` block in `app.js` so it executes after `CREATE TABLE IF NOT EXISTS users`

### 5. authorizeRole Middleware — middleware/auth.js
**Files:** `middleware/auth.js`
**What:** Add and export `authorizeRole(...roles)` after the existing `redirectIfAuthenticated` function

**Before (key section):**
```javascript

    redirectIfAuthenticated
};
```

**After:**
```javascript
const authorizeRole = (...roles) => {
    return (req, res, next) => {
        if (!req.user || !roles.includes(req.user.role)) {
            return res.status(403).json({ error: 'Forbidden' });
        }
        next();
    };
};

module.exports = {
    authenticateToken,
    redirectIfAuthenticated,
    authorizeRole
};
```

- [ ] On subsequent startups against an existing database (with or without the `role` column), the app starts without error — the `ALTER TABLE` error for duplicate column is silently swallowed

- [ ] `POST /login` in `routes/auth.js` produces a JWT whose decoded payload contains `{ userId, email, role }` where `role` equals the value stored in the database

- [ ] `GET /orders/new`, `POST /orders`, `GET /orders`, and `GET /orders/:id` all return 403 for a valid token with `role: 'driver'`

## Test Cases

### Functional (TC-F-XXX)
- **TC-F-001** authorizeRole passes customer: Given `req.user = { id: 1, email: 'a@b.com', role: 'customer' }`, when `authorizeRole('customer')(req, res, next)` is called, then `next()` is invoked exactly once and `res.statusCode` is not 403
- **TC-F-002** authorizeRole blocks driver: Given `req.user = { id: 2, email: 'd@b.com', role: 'driver' }`, when `authorizeRole('customer')(req, res, next)` is called, then `next()` is never called and `res.status(403).json({ error: 'Forbidden' })` is returned
- **TC-F-003** authorizeRole blocks admin: Given `req.user = { id: 3, email: 'a@admin.com', role: 'admin' }`, when `authorizeRole('customer')(req, res, next)` is called, then `next()` is never called and `res.status(403).json({ error: 'Forbidden' })` is returned
- **TC-F-004** app.js JWT includes role: After `POST /login` with valid customer credentials, decode the `token` cookie — the payload must contain `role: 'customer'`
- **TC-F-005** routes/auth.js JWT includes role: After `POST /auth/login` with valid credentials, decode the `token` cookie — the payload must contain `role: 'customer'`
- **TC-F-006** GET /orders/new blocked for driver: Given a signed JWT with `role: 'driver'`, `GET /orders/new` returns 403 JSON `{ error: 'Forbidden' }`
- **TC-F-007** POST /orders blocked for driver: Given a signed JWT with `role: 'driver'`, `POST /orders` with valid body returns 403
- **TC-F-008** GET /orders blocked for driver: Given a signed JWT with `role: 'driver'`, `GET /orders` returns 403
- **TC-F-009** GET /orders/:id blocked for driver: Given a signed JWT with `role: 'driver'`, `GET /orders/1` returns 403
- **TC-F-010** All order routes succeed for customer: Given a signed JWT with `role: 'customer'`, all four order endpoints behave identically to their pre-RBAC behaviour

### Edge Cases (TC-E-XXX)
- **TC-E-001** authorizeRole with missing role field: Given `req.user = { id: 1, email: 'a@b.com' }` (no `role` key), when `authorizeRole('customer')(req, res, next)` is called, then `res.status(403).json({ error: 'Forbidden' })` is returned and `next()` is not called
- **TC-E-002** authorizeRole with null req.user: Given `req.user = null` or `req.user = undefined`, when `authorizeRole('customer')(req, res, next)` is called, then 403 is returned without throwing
- **TC-E-003** ALTER TABLE migration idempotency: Start app against a database that already has the `role` column; verify app startup completes without error and no crash occurs on the `ALTER TABLE` statement
- **TC-E-004** New user defaults to customer: After `POST /signup` with valid credentials, run `SELECT role FROM users WHERE email = ?` — the result must be `'customer'`
- **TC-E-005** authorizeRole multi-role list: Given `authorizeRole('customer', 'admin')` and `req.user.role = 'admin'`, `next()` is called; for `role = 'driver'`, 403 is returned

### Regression (TC-R-XXX)
- **TC-R-001** authenticateToken in middleware/auth.js unchanged: `authenticateToken` still redirects to `/login` for missing/invalid/expired tokens and populates `req.user` for valid tokens — existing `test/middleware.test.js` suite must pass without modification
- **TC-R-002** Non-order authenticated routes unaffected: `GET /dashboard` and `GET /profile` use the inline `authenticateToken` in `app.js` (not `authorizeRole`) and must remain accessible for tokens with any role value
- **TC-R-003** Unauthenticated order routes still redirect to login: A request to `GET /orders/new` with no token must receive a 302 redirect to `/login` (from `authenticateToken`), not a 403 (from `authorizeRole`)

## Risk and Deployment
**Risk Level:** LOW

**Deployment Order:**
1. Deploy updated code — `CREATE TABLE IF NOT EXISTS users` now includes `role` for new databases
2. On startup the `ALTER TABLE users ADD COLUMN role` migration runs automatically for existing databases — no manual migration step required
3. Old JWTs still in cookie jars (issued before this deploy) will not contain a `role` claim; a request with such a token will hit `authorizeRole` with `req.user.role = undefined` and receive 403 — affected users need to log out and log in again to receive a new token with `role` embedded (expected; session invalidation is acceptable for this low-traffic app)

**Rollback Plan:**
1. Revert to previous commit and redeploy
2. The `role` column remains in the database but is unused — no data loss, no schema rollback needed
3. Remove the `role` column only if absolutely necessary via `CREATE TABLE users_backup AS SELECT id, name, email, password, created_at FROM users; DROP TABLE users; ALTER TABLE users_backup RENAME TO users;`

**Key Risks:**
- Old tokens without `role` will receive 403 on order routes after deploy: mitigated by short JWT TTL (24 h) and the fact that users can simply log out and log in; document in release notes
- SQLite ALTER TABLE error-swallowing masks legitimate errors: mitigation is the conditional check `!err.message.includes('duplicate column name')` which re-logs any other error
- `app.js` inline `authenticateToken` is not consolidated with `middleware/auth.js` version: out of scope; tracked as a follow-up refactor to avoid drift between the two implementations
- `User.findAll()` returns rows without `role`: acceptable because no admin list view is built in this task; must be added before any admin UI is implemented

## Scope Boundaries
**In Scope:**
- Add `role TEXT NOT NULL DEFAULT 'customer'` column to users table DDL in all four files
- Idempotent `ALTER TABLE users ADD COLUMN role` migration in `app.js` startup block
- `authorizeRole(...roles)` middleware function added to and exported from `middleware/auth.js`
- `role: user.role` added to `jwt.sign()` payload in `app.js` `POST /login` and `routes/auth.js` `POST /login`
- `authorizeRole('customer')` chained on `GET /orders/new`, `POST /orders`, `GET /orders`, `GET /orders/:id` in `app.js`

**Out of Scope:**
- New routes of any kind (driver status-update endpoint, admin user-list or promote endpoints)
- Admin promotion UI or any view/template changes
- Consolidating the three separate `authenticateToken` implementations (`app.js` inline, `middleware/auth.js`, `routes/dashboard.js` inline)
- Adding `role` to `User.findAll()` SELECT column list
- Signup-time role selection
- Any UI indication of the user's role

**Assumptions:**
- Three roles are defined: `customer`, `driver`, `admin` — all three string literals must be valid values in the system even though only `customer` is gated in this task
- All new users default to `customer`; no administrative tooling to change roles is required in this task
- HTTP 403 JSON `{ error: 'Forbidden' }` is acceptable for browser clients on order routes (no redirect to an error page)
- Existing users without a `role` column will receive `DEFAULT 'customer'` via the `ALTER TABLE` migration, making them customers
- The app runs as a single process (no distributed cache); the in-memory inline `authenticateToken` in `app.js` and the one in `middleware/auth.js` both read from the same JWT secret env var
