# Add /health liveness endpoint

## Summary
Adds a lightweight, unauthenticated `GET /health` endpoint to the Express application that returns HTTP 200 with a JSON body containing `status`, `uptime`, and `timestamp`. This endpoint serves as a liveness probe for load balancers, container orchestrators (Kubernetes, ECS), and external uptime monitors. It deliberately performs no database or downstream dependency checks so that process-level liveness is decoupled from data-plane readiness, preventing cascading restarts when the database is transiently slow.

## Objective
- Provide a single, stable `/health` route usable by Kubernetes `livenessProbe`, load balancer health checks, and uptime monitors.
- Return a response in under 10ms (no I/O, no DB) and under 200 bytes of payload.
- Ensure the endpoint is reachable without any authentication token or session cookie.
- Keep the implementation isolated so it never fails due to application state (DB down, cache down, etc.).

## Business Logic

### Liveness semantics
- Rule: `/health` MUST return HTTP 200 whenever the Node.js process is running and able to service HTTP requests, regardless of database connectivity.
- Rule: Response body MUST include exactly three fields: `status` (string, literal `"ok"`), `uptime` (number, from `process.uptime()` in seconds), and `timestamp` (ISO-8601 UTC string from `new Date().toISOString()`).
- Rule: Endpoint MUST NOT require authentication (no JWT cookie, no session).
- Rule: Only `GET` is supported; other HTTP verbs fall through to the existing 404 handler.
- Rule: Endpoint MUST NOT set any cookies (no `token`, no session) and MUST NOT redirect.

### Operational contract
- Rule: Response latency budget is p99 < 10ms on warm process.
- Rule: No DB connection is opened during the request.
- Rule: No logging is performed on success to avoid log spam from probes (default behaviour of Express route with no explicit logger).

## Acceptance Criteria
- [ ] Given the server is running, when a client issues `GET /health`, then the response status is 200.
- [ ] Given a `GET /health` response, when the body is parsed as JSON, then it contains `status === "ok"`.
- [ ] Given a `GET /health` response, when inspected, then `body.uptime` is a finite, non-negative number.
- [ ] Given a `GET /health` response, when inspected, then `body.timestamp` matches ISO-8601 and round-trips via `new Date().toISOString()`.
- [ ] Given a request with no cookies, when `GET /health` is called, then the response is 200 (no redirect, no 401).
- [ ] Given a `GET /health` response, when headers are inspected, then no `Set-Cookie: token=` header is present.
- [ ] Given a `POST /health` request, when handled, then the response status is 404.
- [ ] Given a `PUT /health` or `DELETE /health` request, when handled, then the response status is 404.
- [ ] Given the database is unavailable, when `GET /health` is called, then the response is still 200.
- [ ] Given the endpoint is mounted, when the response is inspected, then `Content-Type` contains `application/json`.
- [ ] Given the route registration order, when `/health` is hit, then it resolves before the 404 catch-all middleware.

## Risk and Deployment
**Risk Level:** LOW
**Deployment Order:**
1. Merge PR to `main`.
2. Deploy the updated Node.js service (rolling deploy).
3. Update Kubernetes deployment manifest / load balancer target group to point `livenessProbe` (or HTTP health check) at `GET /health`.
4. Monitor probe success rate for 24 hours.

**Rollback Plan:**
- Revert the merge commit (`git revert 72da1a6`) and redeploy. The endpoint is additive and has no data or schema impact, so rollback is safe at any time.
- If only the probe config is problematic, revert the Kubernetes/LB change and leave the endpoint in place.

**Key Risks:**
- Route-ordering regression (`/health` shadowed by a catch-all): mitigated by the TC-F/TC-E tests and by registering before the 404 middleware.
- Probe storm log spam: mitigated by handler issuing no logs; if access logs are noisy, add a path filter in the access logger.
- Accidental inclusion of secrets in response: mitigated by the fixed three-field response schema and test assertions.

## Scope Boundaries
**In Scope:**
- `GET /health` endpoint in `app.js`.
- Automated tests in `test/routes.test.js`.
- Response schema: `{ status, uptime, timestamp }`.

**Out of Scope:**
- A separate `/ready` readiness endpoint that checks DB connectivity.
- Dependency checks (SQLite ping, external API pings).
- Metrics/Prometheus endpoint (`/metrics`).
- Authentication, rate limiting, or IP allow-listing on `/health`.
- Kubernetes manifest changes (handled by infra team).

**Assumptions:**
- Express app is the only HTTP entry point; no reverse-proxy-level rewrites conflict with `/health`.
- `process.uptime()` and `Date.prototype.toISOString()` are available (Node 10+, trivially satisfied).
- `supertest` and `jest` remain the test toolchain.
