# Confirm and harden GET /health endpoint with status and uptime

## Summary
Add (or, more precisely, confirm and harden) a public `GET /health` liveness endpoint that returns HTTP 200 with a JSON body containing `status: "ok"` and `uptime` measured in seconds since process start. An implementation already exists in `app.js` lines 397-403 returning `{ status, uptime, timestamp }`, but it is currently untested and the `uptime` value is a floating-point number from `process.uptime()`. This ticket formalises the contract, normalises `uptime` to an integer number of seconds for predictable consumption by load balancers and uptime monitors, and adds a Jest+supertest functional test to lock the contract in place.

## Objective
- Guarantee a stable `GET /health` contract returning `{ status: "ok", uptime: <integer seconds> }` so external probes (load balancers, k8s-style liveness checks, uptime monitors) can rely on a fixed shape.
- Eliminate ambiguity in the `uptime` field by coercing `process.uptime()` (float seconds) to `Math.floor()` integer seconds.
- Add at least one functional Jest+supertest test to `test/app.test.js` so the endpoint is regression-protected; today there is zero coverage of `/health`.

## Business Logic

### Health Endpoint Contract
- Rule: HTTP method is `GET` only; other methods (POST/PUT/DELETE) fall through to the 404 handler.
- Rule: Path is exactly `/health` (no trailing slash variant required; Express handles both by default).
- Rule: Response status MUST be `200` whenever the Node process is alive enough to handle the request — there are no failure conditions in this endpoint.
- Rule: Response `Content-Type` MUST be `application/json` (Express `res.json()` sets this automatically).
- Rule: Response body MUST be a JSON object with exactly two required keys: `status` (string, always `"ok"`) and `uptime` (integer, seconds since process start, ≥ 0).
- Rule: `uptime` is computed as `Math.floor(process.uptime())` — integer seconds, never a float, never negative.
- Rule: The `timestamp` field currently returned (ISO-8601 string) MAY remain for backward compatibility but is not part of the formal contract.

### Authentication and Dependencies
- Rule: Endpoint is unauthenticated — no JWT cookie required, no `authenticateToken` middleware applied.
- Rule: Endpoint MUST NOT touch the SQLite database; it must respond even if `db` is unreachable.
- Rule: Endpoint MUST be registered before the catch-all 404 middleware at `app.js` line 406 to avoid being shadowed.

## Required Code Changes

### API Route — Harden /health handler
**Files:** `/tmp/delivvr-test1/app.js`
**What:** Coerce `process.uptime()` to an integer with `Math.floor()` so the contract field `uptime` is always a non-negative integer number of seconds. Keep the existing position (before the 404 handler) and the existing `timestamp` field for backward compatibility.

**Before (lines 396-403):**
```javascript
// Health / liveness endpoint — unauthenticated, DB-independent.
app.get('/health', (req, res) => {
    res.status(200).json({
        status: 'ok',
        uptime: process.uptime(),
        timestamp: new Date().toISOString()
    });
});
```

**After:**
```javascript
// Health / liveness endpoint — unauthenticated, DB-independent.
// Contract: 200 { status: "ok", uptime: <integer seconds since process start> }.
// `timestamp` is informational and not part of the formal contract.
app.get('/health', (req, res) => {
    res.status(200).json({
        status: 'ok',
        uptime: Math.floor(process.uptime()),
        timestamp: new Date().toISOString()
    });
});
```

## Acceptance Criteria
- [ ] Given the server is running, when a client sends `GET /health`, then the response status code is `200`.
- [ ] Given the server is running, when a client sends `GET /health`, then the response `Content-Type` header matches `application/json`.
- [ ] Given the server is running, when a client sends `GET /health`, then the response body is a JSON object whose `status` property equals the string `"ok"`.
- [ ] Given the server is running, when a client sends `GET /health`, then the response body's `uptime` property is a non-negative integer (`Number.isInteger(uptime) === true && uptime >= 0`).
- [ ] Given the server has been running for at least 2 seconds, when a client sends `GET /health`, then `uptime >= 2`.
- [ ] Given no auth cookie or `Authorization` header is sent, when a client sends `GET /health`, then the request is not redirected to `/login` and still returns `200`.
- [ ] Given the SQLite database connection is unavailable, when a client sends `GET /health`, then the endpoint still returns `200` (no DB query is made in the handler).
- [ ] Given a client sends `POST /health`, `PUT /health`, or `DELETE /health`, then the catch-all middleware returns `404` (the 404 view).
- [ ] The `/health` route remains registered before the catch-all 404 middleware in `app.js`.
- [ ] The new Jest test block runs as part of `npm test` and all assertions pass on the first invocation.
- [ ] No regression in existing routes: `GET /`, `GET /login`, `GET /signup` continue to render their EJS views with status `200`.

## Test Cases

### Functional (TC-F-XXX)
- **TC-F-001** Happy-path 200 response: start app → `GET /health` via supertest → expect `status === 200`, `body.status === 'ok'`, `Number.isInteger(body.uptime)`, `body.uptime >= 0`.
- **TC-F-002** Content-Type is JSON: `GET /health` → expect `headers['content-type']` matches `/application\/json/`.
- **TC-F-003** Uptime grows over time: capture `body.uptime` from a first call, wait 1100 ms, second call → expect second `body.uptime >= first body.uptime` (allowing equality due to integer flooring at second boundaries).
- **TC-F-004** No authentication required: send `GET /health` with no cookies and no `Authorization` header → expect `200` (not a redirect to `/login`).
- **TC-F-005** Endpoint is DB-independent: even with a stubbed/disconnected `db` module, `GET /health` → expect `200` (the handler never references `db`).

### Edge Cases (TC-E-XXX)
- **TC-E-001** Non-GET method on /health: `POST /health` with empty body → expect `404` (falls through to the 404 view handler at `app.js:406`).
- **TC-E-002** Trailing slash variant: `GET /health/` → expect `200` (Express default routing accepts both).
- **TC-E-003** Uptime immediately after boot: call `GET /health` synchronously after `app.listen` → expect `body.uptime >= 0` and not negative or `NaN` (verifies `Math.floor` of a sub-second float).

### Regression (TC-R-XXX)
- **TC-R-001** Homepage still renders: `GET /` → expect `200` and body contains `Sign Up` and `Login` (matches existing `test/app.test.js` expectations).
- **TC-R-002** 404 fallthrough still works: `GET /this-route-does-not-exist` → expect `404` and the rendered 404 view (proves the new route ordering did not break the catch-all).

## Risk and Deployment
**Risk Level:** LOW
**Deployment Order:**
1. Merge code change to `app.js` (single-file, additive change to integer cast).
2. Merge `package.json` devDependency additions and `npm install` in CI.
3. Run `npm test` and confirm green before deploy.
4. Deploy app server — no migrations, no env-var changes, no schema impact.

**Rollback Plan:** Single revert of the merge commit restores the previous `process.uptime()` float behaviour. No data migration to undo. No external consumers are guaranteed to depend on `uptime` being a float, so revert is safe.

**Key Risks:**
- Risk: An external monitor parses `uptime` as a strict float and breaks on integer. Mitigation: integer is a valid JSON number; any monitor treating `1.234` and `1` as numbers will continue to work.
- Risk: Adding `jest`/`supertest` as devDependencies pulls in transitive packages. Mitigation: lockfile pinning; install is dev-only and not shipped to production.
- Risk: The new test relies on `JWT_SECRET` being set in the test environment because `app.js` exits at lines 14-17 if missing. Mitigation: ensure `test/jest-setup.js` (or CI env) sets `JWT_SECRET=test-secret` before requiring `app.js`.
