# Order creation — authenticated users place delivery orders

## Summary
This change introduces the first end-to-end order lifecycle primitive in Delivvr: authenticated users can fill out a form capturing pickup address, delivery address, and an optional package description, submit it, and immediately see their new order listed on a `GET /orders` page. It persists orders in a new `orders` SQLite table linked by `user_id` to the existing `users` table, wires up dashboard statistics ("Active Deliveries", "Pending Pickups") to real database counts instead of hard-coded placeholder numbers, and adds a "Place Order" CTA on the dashboard. The key design decision is to keep parity with the existing project conventions: routes remain defined inline in `app.js`, a new `models/Order.js` follows the class-with-static-methods pattern established by `models/User.js`, validation uses `express-validator` `body()` chains, and all views reuse the existing Material Design (`md-*`) CSS system.

## Objective
- Deliver a protected `/orders/new` form, `POST /orders` submission handler, and `/orders` listing route, all gated behind the existing `authenticateToken` middleware so unauthenticated users are redirected to `/login`.
- Persist each submission into a newly created `orders` SQLite table (created at boot via `db.serialize()`) with `user_id`, `pickup_address`, `delivery_address`, `package_description`, `status='pending'`, and `created_at` columns, with no orphan rows (FK to `users(id)`).
- Replace the hard-coded `3` and `2` values in the dashboard's "Active Deliveries" and "Pending Pickups" stat cards with live counts for the current user from the `orders` table, and surface a "Place Order" CTA linking to `/orders/new`.

## Business Logic

### Order Creation
- Rule: Only authenticated users (valid JWT in `req.cookies.token`) can access `GET /orders/new`, `POST /orders`, or `GET /orders`. Unauthenticated requests are 302-redirected to `/login` via the existing `authenticateToken` middleware.
- Rule: `pickup_address` must be a trimmed, non-empty string between 3 and 500 characters inclusive. Rejection returns the form with an inline error and HTTP 200 (follows the existing `signup`/`login` re-render pattern, not a 400 JSON).
- Rule: `delivery_address` must be a trimmed, non-empty string between 3 and 500 characters inclusive. Same rejection semantics as above.
- Rule: `package_description` is OPTIONAL. When present, it is trimmed and capped at 1000 characters; when absent/empty after trim, it is persisted as `NULL`.
- Rule: On successful insert, a row is created with `status = 'pending'` (hard-coded — not accepted from the form payload) and `created_at` defaulted by SQLite via `CURRENT_TIMESTAMP`. The response is a 302 redirect to `/orders`.
- Rule: DB errors (`err` callback arg non-null on `INSERT`) must log via `console.error` and re-render `orders-new.ejs` with `error = 'Failed to create order. Please try again.'` — never leak the raw driver error to the user.

### Order Listing
- Rule: `GET /orders` lists orders WHERE `user_id = req.user.id`, ordered by `created_at DESC`. A user MUST NEVER see another user's orders.
- Rule: If the user has zero orders, the page renders an empty-state card with a "Place your first order" CTA linking to `/orders/new` — no silent blank page.
- Rule: Each row displays `id`, `pickup_address`, `delivery_address`, `package_description` (falling back to "—" if NULL), `status` (rendered via the existing `.md-chip.md-chip-pending` for `pending`), and a localized `created_at`.

### Dashboard Stats
- Rule: "Active Deliveries" count = number of rows where `user_id = req.user.id` AND `status IN ('pending','in_transit','out_for_delivery')`. Given the current scope only emits `'pending'`, this effectively equals the pending count today, but the query is future-proofed.
- Rule: "Pending Pickups" count = number of rows where `user_id = req.user.id` AND `status = 'pending'`.
- Rule: Both counts default to `0` (never `undefined`) when the user has no orders, so the EJS template can render `<%= count %>` safely.
- Rule: The "Place Order" quick action MUST be rendered as an `<a href="/orders/new">` (not a disabled `<button>`), using the `.md-button--contained` (primary, filled) variant to make it the visually dominant CTA in the Quick Actions card.

**After:**
```javascript
// models/Order.js
// Order model — wraps the shared sqlite3 db handle provided by app.js.
// Follows the static-method Promise pattern from models/User.js.

const ACTIVE_STATUSES = ['pending', 'in_transit', 'out_for_delivery'];

function createOrderModel(db) {
    class Order {
        static create(userId, { pickup_address, delivery_address, package_description }) {
            return new Promise((resolve, reject) => {
                const desc = (package_description && package_description.trim()) || null;
                db.run(
                    `INSERT INTO orders (user_id, pickup_address, delivery_address, package_description, status)
                     VALUES (?, ?, ?, ?, 'pending')`,
                    [userId, pickup_address.trim(), delivery_address.trim(), desc],
                    function (err) {
                        if (err) return reject(err);
                        resolve({ id: this.lastID, user_id: userId, status: 'pending' });
                    }
                );
            });
        }

        static findByUserId(userId) {
            return new Promise((resolve, reject) => {
                db.all(
                    `SELECT id, user_id, pickup_address, delivery_address, package_description, status, created_at
                     FROM orders WHERE user_id = ? ORDER BY created_at DESC`,
                    [userId],
                    (err, rows) => (err ? reject(err) : resolve(rows))
                );
            });
        }

        static findById(id) {
            return new Promise((resolve, reject) => {
                db.get(
                    `SELECT id, user_id, pickup_address, delivery_address, package_description, status, created_at
                     FROM orders WHERE id = ?`,
                    [id],
                    (err, row) => (err ? reject(err) : resolve(row))
                );
            });
        }

        static countActiveByUserId(userId) {
            return new Promise((resolve, reject) => {
                const placeholders = ACTIVE_STATUSES.map(() => '?').join(',');
                db.get(
                    `SELECT COUNT(*) AS c FROM orders WHERE user_id = ? AND status IN (${placeholders})`,
                    [userId, ...ACTIVE_STATUSES],
                    (err, row) => (err ? reject(err) : resolve(row ? row.c : 0))
                );
            });
        }

        static countPendingByUserId(userId) {
            return new Promise((resolve, reject) => {
                db.get(
                    `SELECT COUNT(*) AS c FROM orders WHERE user_id = ? AND status = 'pending'`,
                    [userId],
                    (err, row) => (err ? reject(err) : resolve(row ? row.c : 0))
                );
            });
        }
    }

    return Order;
}

module.exports = createOrderModel;
module.exports.ACTIVE_STATUSES = ACTIVE_STATUSES;
```

**After:**
```javascript
const createOrderModel = require('./models/Order');
const Order = createOrderModel(db);

const orderValidation = [
    body('pickup_address')
        .trim()
        .isLength({ min: 3, max: 500 })
        .withMessage('Pickup address must be between 3 and 500 characters'),
    body('delivery_address')
        .trim()
        .isLength({ min: 3, max: 500 })
        .withMessage('Delivery address must be between 3 and 500 characters'),
    body('package_description')
        .optional({ checkFalsy: true })
        .trim()
        .isLength({ max: 1000 })
        .withMessage('Package description must be 1000 characters or fewer')
];

app.get('/dashboard', authenticateToken, async (req, res) => {
    db.get('SELECT id, name, email, created_at FROM users WHERE id = ?', [req.user.id], async (err, user) => {
        if (err || !user) {
            console.error('Dashboard user lookup failed:', err);
            return res.redirect('/login');
        }
        try {
            const [activeDeliveriesCount, pendingPickupsCount] = await Promise.all([
                Order.countActiveByUserId(req.user.id),
                Order.countPendingByUserId(req.user.id)
            ]);
            res.render('dashboard', { user, activeDeliveriesCount, pendingPickupsCount });
        } catch (countErr) {
            console.error('Dashboard count query failed:', countErr);
            res.render('dashboard', { user, activeDeliveriesCount: 0, pendingPickupsCount: 0 });
        }
    });
});

app.get('/orders/new', authenticateToken, (req, res) => {
    res.render('orders-new', { error: null, values: { pickup_address: '', delivery_address: '', package_description: '' } });
});

app.post('/orders', authenticateToken, orderValidation, async (req, res) => {
    const errors = validationResult(req);
    const values = {
        pickup_address: req.body.pickup_address || '',
        delivery_address: req.body.delivery_address || '',
        package_description: req.body.package_description || ''
    };
    if (!errors.isEmpty()) {
        return res.render('orders-new', { error: errors.array()[0].msg, values });
    }
    try {
        await Order.create(req.user.id, values);
        return res.redirect('/orders');
    } catch (e) {
        console.error('Order creation failed:', e);
        return res.render('orders-new', { error: 'Failed to create order. Please try again.', values });
    }
});

app.get('/orders', authenticateToken, async (req, res) => {
    try {
        const orders = await Order.findByUserId(req.user.id);
        res.render('orders-list', { orders, user: { id: req.user.id, email: req.user.email } });
    } catch (e) {
        console.error('Order list failed:', e);
        res.render('orders-list', { orders: [], user: { id: req.user.id, email: req.user.email }, error: 'Failed to load orders.' });
    }
});
```

## Acceptance Criteria
- [ ] Given an unauthenticated visitor, when they request `GET /orders/new`, then they are 302-redirected to `/login`.
- [ ] Given an unauthenticated visitor, when they request `GET /orders` or `POST /orders`, then they are 302-redirected to `/login`.
- [ ] Given an authenticated user, when they request `GET /orders/new`, then the response renders `orders-new.ejs` with HTTP 200 and contains `<form action="/orders" method="POST">`.
- [ ] Given an authenticated user submitting a valid payload (pickup_address="123 A St", delivery_address="456 B Ave", package_description="Fragile"), when they `POST /orders`, then exactly one row is inserted into `orders` with `user_id = req.user.id`, `status = 'pending'`, and the user is 302-redirected to `/orders`.
- [ ] Given an authenticated user submitting `pickup_address=""`, when they `POST /orders`, then no DB row is written and the form re-renders with the error "Pickup address must be between 3 and 500 characters".
- [ ] Given an authenticated user with 2 pending orders, when they `GET /orders`, then the rendered page contains exactly 2 `.md-list-item` rows ordered by `created_at DESC`.
- [ ] Given user A with 1 order and user B with 0 orders, when user B `GET /orders`, then user B sees the empty-state card and NONE of user A's data.
- [ ] Given an authenticated user, when they `GET /dashboard`, then the "Active Deliveries" and "Pending Pickups" stat cards show counts from `Order.countActiveByUserId` / `Order.countPendingByUserId` (not the literals `3` and `2`).
- [ ] Given an authenticated user on the dashboard, when they click "Place Order" in Quick Actions, then the browser navigates to `/orders/new`.
- [ ] Given `app.js` starts against a fresh database file, when the process boots, then the `orders` table exists with the specified columns (verifiable via `PRAGMA table_info(orders)`).
- [ ] Given an authenticated user submitting a payload with `package_description="   "` (whitespace), when they `POST /orders`, then the row is inserted with `package_description = NULL`.
- [ ] Given a DB error during INSERT (simulated by temporarily locking the DB), when POST /orders runs, then the form re-renders with "Failed to create order. Please try again." and no crash.

## Risk and Deployment
**Risk Level:** LOW
**Deployment Order:**
1. Merge code to main — the `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` statements run automatically inside `db.serialize()` at boot; no separate migration job is needed.
2. Restart the Node process — tables and indexes are created idempotently on first startup.
3. Smoke-test `GET /orders/new`, `POST /orders`, `GET /orders`, `GET /dashboard` using a test account.
4. Monitor application logs for any "Order creation failed" or "Dashboard count query failed" entries for 30 minutes.

**Rollback Plan:** Revert the merge commit and restart the service. The `orders` table will remain in the SQLite file but is inert (no code paths reference it); no data cleanup is required. If rollback happens after users have placed orders and we want to discard them, execute `DROP TABLE orders;` manually against `database.sqlite` after the revert.

**Key Risks:**
- Risk: Hard-coded "3" / "2" literals remain somewhere in `dashboard.ejs` after edit. Mitigation: grep the template after edit for `>3<` and `>2<` inside stat-card blocks; TC-F-004 fails fast if counts are not wired.
- Risk: `models/User.js` opens a separate `database.db` connection — developers may assume `models/Order.js` should do the same and create a second file. Mitigation: `models/Order.js` uses a factory that takes the `db` handle from `app.js`, and the PRD explicitly calls this out.
- Risk: EJS XSS via unsanitized address text. Mitigation: all output uses `<%= %>` (HTML-escaped); unit test TC-E-003 asserts this.
- Risk: Missing index causes slow dashboard counts at scale. Mitigation: `CREATE INDEX IF NOT EXISTS idx_orders_user_status ON orders(user_id, status)` added alongside the table.

## Scope Boundaries
**In Scope:**
- `GET /orders/new` form, `POST /orders` submission, `GET /orders` listing.
- `orders` SQLite table + two indexes, bootstrapped in `app.js` `db.serialize()`.
- `models/Order.js` factory with `create`, `findByUserId`, `findById`, `countActiveByUserId`, `countPendingByUserId`.
- Dashboard stat cards wired to `Order.countActiveByUserId` and `Order.countPendingByUserId`.
- "Place Order" CTA and "My Orders" link in the dashboard Quick Actions card.
- Server-side validation via `express-validator` on pickup/delivery address and optional description.

**Out of Scope:**
- Order status transitions (pending → in_transit → delivered) and any admin/driver-side UI.
- Order editing, cancellation, or deletion by the user.
- Payments, pricing, or invoicing.
- Real-time delivery tracking, maps, geocoding, or distance calculation.
- Email/SMS/push notifications on order creation.
- Pagination, filtering, or search on `/orders`.
- A dedicated `/orders/:id` detail page.
- REST/JSON API equivalents — this is server-rendered only.

**Assumptions:**
- The existing SQLite file `database.sqlite` is writable by the Node process and persists across restarts.
- `JWT_SECRET` is already configured in all environments (the process exits on boot otherwise — per lines 14-18 of `app.js`).
- No ORM will be introduced; raw `sqlite3` with parameterized queries remains the norm.
- Users are identified solely by `req.user.id` from the decoded JWT; no per-request DB lookup is needed for authorization on these routes.
