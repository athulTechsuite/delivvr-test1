# Add RBAC Admin UI for Managing User Roles

## Summary

This feature completes the role-based access control (RBAC) system in the Node.js/Express delivery management app by adding a user-role management admin UI. The RBAC backbone — `middleware/auth.js` with `authenticateToken` (live DB role lookup) and `requireRole('admin')`, the `role TEXT NOT NULL DEFAULT 'user'` column in the `users` table, and the `views/403.ejs` access-denied page — is already implemented and in production. The only missing piece is an admin interface to view and change user roles. This PRD specifies adding `GET /admin/users` and `POST /admin/users/:id/role` routes, fixing the `User.findAll()` query to expose the `role` field, adding a `User.updateRole()` method, creating `views/admin-users.ejs`, and adding a conditional admin nav section to `views/layout.ejs`. Without this UI, role promotion and demotion requires direct database access, making the RBAC foundation operationally incomplete.

## Objective

- Admin users can view a full table of all registered users (name, email, role, created_at) at `GET /admin/users`, protected by `[authenticateToken, requireRole('admin')]`
- Admin users can change any user's role between the two permitted values — `'user'` and `'admin'` — via `POST /admin/users/:id/role`, with server-side validation rejecting any other value with a 400 response
- The sidebar in `views/layout.ejs` conditionally renders admin navigation links (Orders, Users) only when `user.role === 'admin'`, preventing UI exposure to regular users

## Business Logic

### Role Validation
- Rule: The only permitted role values are exactly `'user'` and `'admin'`. Any other string (including `'superadmin'`, `'moderator'`, empty string) must be rejected with HTTP 400 before touching the database.
- Rule: Validation occurs at the route handler level in `app.js` before calling `User.updateRole()`, and also inside `User.updateRole()` itself as a defence-in-depth guard.

### Access Control
- Rule: `GET /admin/users` and `POST /admin/users/:id/role` must be registered behind `[authenticateToken, requireRole('admin')]`. Any authenticated non-admin receives a 403 rendered via `views/403.ejs`. Any unauthenticated request is redirected to `/login` by `authenticateToken`.
- Rule: Role changes take effect immediately on the next authenticated request because `authenticateToken` performs a live `SELECT role FROM users WHERE id = ?` database lookup on every request and never trusts the JWT payload for the role field.

### User Listing
- Rule: `User.findAll()` must return `id, name, email, role, created_at` for every row. The current query (`SELECT id, name, email, created_at FROM users`) is missing `role` and must be updated. No sort order or pagination is required; results return in SQLite insertion order.

### Role Update
- Rule: `User.updateRole(id, role)` runs `UPDATE users SET role = ? WHERE id = ?` and resolves with `{ changes: this.changes }`. It must reject the Promise if role is not in `['user', 'admin']`. If `changes === 0` (user id not found), the calling route handler should return a 404.

// Get all users (for admin purposes)
static findAll() {
    return new Promise((resolve, reject) => {
        db.all('SELECT id, name, email, role, created_at FROM users', (err, rows) => {
            if (err) {
                reject(err);
            } else {
                resolve(rows);
            }
        });
    });
}

// Update a user's role — role must be one of ['user', 'admin']
static updateRole(id, role) {
    const VALID_ROLES = ['user', 'admin'];
    return new Promise((resolve, reject) => {
        if (!VALID_ROLES.includes(role)) {
            return reject(new Error(`Invalid role '${role}'. Must be one of: ${VALID_ROLES.join(', ')}`));
        }
        db.run('UPDATE users SET role = ? WHERE id = ?', [role, id], function(err) {
            if (err) {
                reject(err);
            } else {
                resolve({ changes: this.changes });
            }
        });
    });
}
```

// Admin routes
app.get('/admin/orders', authenticateToken, requireRole('admin'), async (req, res) => {
    try {
        const orders = await Order.findAll();
        res.render('admin-orders', { user: req.user, orders });
    } catch (err) {
        console.error('Error loading admin orders:', err);
        res.render('admin-orders', { user: req.user, orders: [] });
    }

app.get('/admin/users', authenticateToken, requireRole('admin'), async (req, res) => {
    try {
        const users = await User.findAll();
        res.render('admin-users', { user: req.user, users });
    } catch (err) {
        console.error('Error loading admin users:', err);
        res.render('admin-users', { user: req.user, users: [] });
    }
});

app.post('/admin/users/:id/role', authenticateToken, requireRole('admin'), async (req, res) => {
    const VALID_ROLES = ['user', 'admin'];
    const { role } = req.body;
    const rawId = req.params.id;
    const parsedId = Number.parseInt(rawId, 10);

    if (
        !Number.isInteger(parsedId) ||
        parsedId <= 0 ||
        String(parsedId) !== String(rawId).trim()
    ) {
        return res.status(404).render('404');
    }

    if (!role || !VALID_ROLES.includes(role)) {
        return res.status(400).render('admin-users', {
            user: req.user,
            users: [],
            error: `Invalid role. Must be one of: ${VALID_ROLES.join(', ')}`
        });
    }

    try {
        const result = await User.updateRole(parsedId, role);
        if (result.changes === 0) {
            return res.status(404).render('404');
        }
        return res.redirect('/admin/users');
    } catch (err) {
        console.error('Error updating user role:', err);
        return res.status(500).render('admin-users', {
            user: req.user,
            users: [],
            error: 'Failed to update user role'
        });
    }
});
```

## Acceptance Criteria

- [ ] `GET /admin/users` with a valid admin token/cookie returns HTTP 200 and renders a table showing all users with the `role` column correctly populated
- [ ] `GET /admin/users` with no token/cookie returns a redirect to `/login` (HTTP 302)
- [ ] `GET /admin/users` with a valid token for a `role='user'` account returns HTTP 403 and renders `views/403.ejs`
- [ ] `POST /admin/users/:id/role` with `body.role = 'admin'` as an admin user updates the target user's DB row to `role='admin'` and redirects (302) to `/admin/users`
- [ ] `POST /admin/users/:id/role` with `body.role = 'user'` as an admin user updates the target user's DB row to `role='user'` and redirects (302) to `/admin/users`
- [ ] `POST /admin/users/:id/role` with `body.role = 'superadmin'` returns HTTP 400
- [ ] `POST /admin/users/:id/role` with a missing `role` field in the POST body returns HTTP 400
- [ ] `POST /admin/users/:id/role` by an authenticated non-admin user returns HTTP 403
- [ ] `User.updateRole(id, 'superadmin')` rejects the Promise with an error message containing the invalid role name
- [ ] `User.findAll()` returns rows that include a `role` field with values `'user'` or `'admin'` for every row
- [ ] The sidebar in `views/layout.ejs` renders "Admin Orders" and "Admin Users" nav links only when the template variable `user.role === 'admin'`
- [ ] The sidebar in `views/layout.ejs` does not render any admin nav links when the user is authenticated but `user.role === 'user'`
- [ ] `GET /admin/orders` continues to return HTTP 200 with the full orders table (regression)
- [ ] `PATCH /orders/:id/status` with a valid status value as an admin continues to return HTTP 200 JSON (regression)

## Risk and Deployment

**Risk Level:** LOW

**Deployment Order:**
1. Deploy updated `models/User.js` (no schema migration needed — `role` column already exists)
2. Deploy updated `app.js` with the two new admin routes and `require('./models/User')` import
3. Deploy new `views/admin-users.ejs`
4. Deploy updated `views/layout.ejs` with conditional admin nav links

**Rollback Plan:** Revert the four changed/added files to their previous state via `git revert` or by re-deploying the prior commit. No database schema changes are made, so no migration rollback is required. Existing sessions are unaffected.

**Key Risks:**
- `User.findAll()` query change adds the `role` field to every returned object. Any existing caller that destructures the result with an exact column check could be affected — audit all `User.findAll()` callsites in `app.js` before deploying (currently `app.js` does not call `User.findAll()`, but the model file is imported by the test suite)
- Admin self-demotion: an admin can POST to `/admin/users/:ownId/role` with `role='user'`, potentially locking out the last admin account. This is acceptable in the current scope but should be addressed in a follow-up with a "cannot remove last admin" guard
- The `models/User.js` uses a separate database connection (`database.db`) while `app.js` connects to `database.sqlite`. In production these must point to the same physical file; verify `DB_PATH` environment variable consistency across modules

## Scope Boundaries

**In Scope:**
- `GET /admin/users` route — list all users with their roles
- `POST /admin/users/:id/role` route — update a specific user's role
- `views/admin-users.ejs` — new EJS view for the users admin page
- `User.findAll()` fix — add `role` to the SELECT clause
- `User.updateRole(id, role)` — new static model method with validation
- Admin nav links in `views/layout.ejs` — conditionally visible for `role='admin'` only

**Out of Scope:**
- Creating new users from the admin UI
- Deleting users from the admin UI
- Adding roles beyond the two existing values `'user'` and `'admin'`
- Pagination, sorting, or search/filter on the users list
- Email notifications when a role is changed
- Audit log for role changes
- Protection against an admin demoting themselves (last-admin guard)

**Assumptions:**
- The `role TEXT NOT NULL DEFAULT 'user'` column already exists in the `users` table in all environments (confirmed from `app.js` line 31 and `models/User.js` line 16)
- `middleware/auth.js` exports `authenticateToken` and `requireRole` with the signatures observed in the current codebase
- All environments have the `DB_PATH` environment variable pointing to the same SQLite file used by both `app.js` and `models/User.js`
- The EJS view engine is configured with `express-ejs-layouts` or equivalent such that standalone HTML documents in `views/` are rendered directly (confirmed: `admin-orders.ejs` is a full standalone HTML document)
