# Add role-based access control (RBAC) to delivery management app

> **Linear:** [TEC-394](https://linear.app/techsuite/issue/TEC-394/add-role-based-access-control-rbac-to-delivery-management-app)

## Summary

Add a two-role RBAC system (`user` / `admin`) to the Delivvr Express/SQLite application. A `role` column is added to the `users` table with a default of `'user'`, the shared `authenticateToken` middleware is updated to perform a live DB lookup of the role on every authenticated request (never from the JWT payload), and a new `requireRole('admin')` middleware gates two new admin-only routes: `GET /admin/orders` (all orders across all users) and `PATCH /orders/:id/status` (admin status updates). This prevents regular users from accessing cross-tenant order data and provides a controlled operational admin interface, with role assignment handled exclusively through a seed script.

## Objective

- All new and existing users have a persisted `role` (`'user'` by default), fetched live from the database on every authenticated request so stale JWT tokens cannot carry elevated privileges.
- Admin users can view all orders via `GET /admin/orders` and update any order's status via `PATCH /orders/:id/status`; non-admin attempts return HTTP 403 and render `views/403.ejs`.
- Role promotion is performed exclusively by running `node database/seed-admin.js <email>` — no signup-flow changes, no self-service UI, and no role field in the JWT payload.

## Business Logic

### Role Storage and Assignment
- **Rule:** The `users` table has a new column `role TEXT NOT NULL DEFAULT 'user'`; every INSERT that omits `role` receives `'user'` automatically.
- **Rule:** Only `database/seed-admin.js` may elevate a user to `'admin'` via `UPDATE users SET role = 'admin' WHERE email = ?`.
- **Rule:** There are exactly two valid role values: `'user'` and `'admin'`. No other role exists in this scope.

### Live Role Lookup
- **Rule:** After JWT verification in `authenticateToken`, a `SELECT role FROM users WHERE id = ?` is executed using `req.user.id` (from the `app.js` JWT convention). The result is attached as `req.user.role` before calling `next()`.
- **Rule:** If the DB lookup finds no row (user deleted after token issuance), the middleware redirects to `/login` — not 403.
- **Rule:** Role is never included in the JWT payload at sign time; `app.js` continues to sign `{ id: user.id, email: user.email }` only.

### requireRole Middleware
- **Rule:** `requireRole(role)` returns a middleware function. If `req.user.role !== role`, it calls `res.status(403).render('403')` and does not call `next()`.
- **Rule:** `requireRole` is always chained after `authenticateToken` — it assumes `req.user` and `req.user.role` are already populated.

### Admin Route: GET /admin/orders
- **Rule:** Returns all orders across all users (not scoped to `user_id`), ordered `created_at DESC`.
- **Rule:** Protected by `[authenticateToken, requireRole('admin')]` middleware chain.

### Admin Route: PATCH /orders/:id/status
- **Rule:** Accepts a JSON body `{ "status": "<value>" }`. The `status` value must be one of the five `Order.STATUS` constants: `pending`, `in_transit`, `out_for_delivery`, `delivered`, `cancelled`. Any other value returns HTTP 400.
- **Rule:** Protected by `[authenticateToken, requireRole('admin')]` middleware chain.
- **Rule:** If the order does not exist, returns 404.

const jwt = require('jsonwebtoken');
const sqlite3 = require('sqlite3').verbose();
const path = require('path');

const DB_PATH = process.env.DB_PATH || path.join(__dirname, '..', 'database.sqlite');
const db = new sqlite3.Database(DB_PATH);

const authenticateToken = (req, res, next) => {
    const authHeader = req.headers['authorization'];
    const token = authHeader && authHeader.split(' ')[1];
    const cookieToken = req.cookies && req.cookies.token;
    const finalToken = token || cookieToken;

    if (!finalToken) {
        return res.redirect('/login');
    }

    const jwtSecret = process.env.JWT_SECRET;
    if (!jwtSecret) {
        console.error('JWT_SECRET environment variable is not set');
        return res.status(500).json({ error: 'Server configuration error' });
    }

    jwt.verify(finalToken, jwtSecret, (err, decoded) => {
        if (err) {
            return res.redirect('/login');
        }
        // Live DB lookup — role is never trusted from the JWT payload.
        db.get('SELECT role FROM users WHERE id = ?', [decoded.id], (dbErr, row) => {
            if (dbErr) {
                console.error('DB error during role lookup:', dbErr);
                return res.status(500).json({ error: 'Server error' });
            }
            if (!row) {
                // User deleted after token was issued.
                return res.redirect('/login');
            }
            req.user = { ...decoded, role: row.role };
            next();
        });
    });
};

const requireRole = (role) => (req, res, next) => {
    if (!req.user || req.user.role !== role) {
        return res.status(403).render('403');
    }
    next();
};

const redirectIfAuthenticated = (req, res, next) => {
    const authHeader = req.headers['authorization'];
    const token = authHeader && authHeader.split(' ')[1];
    const cookieToken = req.cookies && req.cookies.token;
    const finalToken = token || cookieToken;

    if (finalToken) {
        const jwtSecret = process.env.JWT_SECRET;
        if (!jwtSecret) {
            console.error('JWT_SECRET environment variable is not set');
            return res.status(500).json({ error: 'Server configuration error' });
        }
        jwt.verify(finalToken, jwtSecret, (err, user) => {
            if (!err && user) {
                return res.redirect('/dashboard');
            }
            next();
        });
    } else {
        next();
    }
};

module.exports = {
    authenticateToken,
    requireRole,
    redirectIfAuthenticated
};

app.get('/admin/orders', authenticateToken, requireRole('admin'), async (req, res) => {
    try {
        const orders = await Order.findAll();
        res.render('admin-orders', { user: req.user, orders });
    } catch (err) {
        console.error('Error loading admin orders:', err);
        res.render('admin-orders', { user: req.user, orders: [] });

app.patch('/orders/:id/status', authenticateToken, requireRole('admin'), async (req, res) => {
    const rawId = req.params.id;
    const parsedId = Number.parseInt(rawId, 10);

    if (
        !Number.isInteger(parsedId) ||
        parsedId <= 0 ||
        String(parsedId) !== String(rawId).trim()
    ) {
        return res.status(404).json({ error: 'Order not found' });
    }

    const { status } = req.body;
    const validStatuses = Object.values(Order.STATUS);
    if (!status || !validStatuses.includes(status)) {
        return res.status(400).json({
            error: `Invalid status. Must be one of: ${validStatuses.join(', ')}`
        });
    }

    try {
        const updated = await Order.updateStatus(parsedId, status);
        if (!updated) {
            return res.status(404).json({ error: 'Order not found' });
        }
        return res.status(200).json({ success: true, id: parsedId, status });
    } catch (err) {
        console.error('Error updating order status:', err);
        return res.status(500).json({ error: 'Failed to update order status' });
    }
});

                function (err) {
                    if (err) {
                        return reject(err);
                    }
                    resolve(this.changes > 0);
                }
            );
        });
    }

## Acceptance Criteria

- [ ] `GET /admin/orders` returns HTTP 200 and renders `admin-orders.ejs` with all orders when requester has `role = 'admin'` JWT cookie
- [ ] `GET /admin/orders` returns HTTP 403 and renders `views/403.ejs` when requester has `role = 'user'`
- [ ] `GET /admin/orders` redirects to `/login` when no JWT cookie is present
- [ ] `PATCH /orders/:id/status` with body `{ "status": "in_transit" }` returns HTTP 200 and persists the new status for an admin user
- [ ] `PATCH /orders/:id/status` with body `{ "status": "flying" }` returns HTTP 400 with a descriptive error listing valid statuses
- [ ] `PATCH /orders/:id/status` for a non-existent order ID returns HTTP 404
- [ ] `PATCH /orders/:id/status` called by a `role = 'user'` returns HTTP 403 and renders `views/403.ejs`
- [ ] `req.user.role` is populated by a live `SELECT role FROM users WHERE id = ?` query — not from the JWT payload — verified by removing `role` from the `users` table row and confirming redirect to `/login`
- [ ] `database/seed-admin.js user@example.com` sets `role = 'admin'` for the user and logs "Success: user@example.com has been promoted to admin."
- [ ] `database/seed-admin.js unknown@example.com` logs "No user found with email: unknown@example.com" and exits with code 1
- [ ] `views/403.ejs` renders with the same Bootstrap Icons + `md-card` layout as `views/404.ejs`, includes a "Back to Dashboard" link, and the HTTP response status is 403
- [ ] All four `CREATE TABLE IF NOT EXISTS users` DDL blocks (in `app.js`, `config/database.js`, `database/db.js`, `models/User.js`) include `role TEXT NOT NULL DEFAULT 'user'`
- [ ] `database/migrate-add-role.js` runs without error on both a fresh DB (adds column) and an already-migrated DB (logs "already applied")
- [ ] `Order.findAll()` returns all rows from the orders table ordered by `created_at DESC`
- [ ] `Order.updateStatus(id, status)` rejects with an Error for an invalid status string and resolves `false` for a non-existent order ID

## Risk and Deployment

**Risk Level:** MEDIUM

**Deployment Order:**
1. Run `node database/migrate-add-role.js` against the live DB (adds `role` column, safe on fresh or existing data)
2. Deploy updated `middleware/auth.js` (authenticateToken + requireRole)
3. Deploy updated `app.js` (replaces inline authenticateToken, adds admin routes)
4. Deploy updated `models/Order.js` (adds findAll, updateStatus)
5. Deploy updated DDL files (`config/database.js`, `database/db.js`, `models/User.js`)
6. Deploy new views (`views/403.ejs`, `views/admin-orders.ejs`)
7. Promote at least one user to admin via `node database/seed-admin.js <email>`
8. Smoke-test `GET /admin/orders` and `PATCH /orders/:id/status` with the new admin account

**Rollback Plan:**
1. Revert to previous Git commit for application files
2. Run `ALTER TABLE users DROP COLUMN role` if SQLite version ≥ 3.35.0; otherwise recreate table without role column and migrate data
3. Redeploy previous image/build — no JWT changes required since role was never in the token

**Key Risks:**

- **Duplicate authenticateToken in three files (`app.js` inline, `middleware/auth.js`, `routes/dashboard.js` inline):** If any copy is missed, authenticated routes will not set `req.user.role`, causing `requireRole` to always deny. **Mitigation:** Replace all three inline copies with the shared import; add an integration test that hits a protected route through each entry point.
- **Two SQLite DB files (`database.sqlite` and `database/users.db`):** `routes/dashboard.js` opens `database/users.db` while `app.js` uses `DB_PATH → database.sqlite`. **Mitigation:** Confirm canonical DB via `DB_PATH` env var before migration; run `migrate-add-role.js` only against that path; update `routes/dashboard.js` to use the same `database/db.js` module.
- **JWT payload `id` vs `userId` inconsistency:** `app.js` signs `{ id }`, `routes/auth.js` signs `{ userId }`. The role lookup in `authenticateToken` uses `decoded.id`; tokens signed by `routes/auth.js` will have `decoded.id = undefined`, causing the DB lookup to return no row and redirect to `/login`. **Mitigation:** Align `routes/auth.js` to sign `{ id: user.id, email: user.email }` as part of this work.
- **Status injection via PATCH:** Accepting arbitrary strings would corrupt the `status` field. **Mitigation:** Validate against `Object.values(Order.STATUS)` before the UPDATE; return 400 with a whitelist error message.

## Scope Boundaries

**In Scope:**
- Adding `role TEXT NOT NULL DEFAULT 'user'` column to the `users` table and all DDL copies
- Live DB role lookup in `authenticateToken` on every authenticated request
- `requireRole('admin')` middleware rendering `views/403.ejs` with HTTP 403 on access violation
- `GET /admin/orders` — admin sees all orders across all users
- `PATCH /orders/:id/status` — admin can update any order's status to a value in `Order.STATUS`
- `views/403.ejs` error page matching existing `views/404.ejs` style
- `views/admin-orders.ejs` new admin view
- `database/seed-admin.js` seed script for one-shot role promotion
- `database/migrate-add-role.js` idempotent migration script
- Consolidating the three duplicate `authenticateToken` copies into the shared `middleware/auth.js`
- Fixing the `id` / `userId` JWT payload inconsistency between `app.js` and `routes/auth.js`

**Out of Scope:**
- Self-service role promotion (no UI for users to become admins)
- A driver role or any third role beyond `user` / `admin`
- Admin user management UI (create/delete/list users)
- API-key or session-based authentication — JWT cookie flow only
- Role stored in the JWT payload
- Pagination or filtering on `GET /admin/orders`
- Email notifications on status change

**Assumptions:**
- The canonical database is identified by the `DB_PATH` environment variable (defaulting to `database.sqlite` in the project root); `database/users.db` is a legacy artifact of `routes/dashboard.js` and will be retired
- `node database/seed-admin.js` is the only mechanism to create admin users — no automated test or CI flow needs an admin user except where the seed script is called as part of the test setup
- The application runs Node.js with SQLite ≥ 3.35.0 (for potential `ALTER TABLE … DROP COLUMN` rollback), or the team accepts the recreate-and-migrate rollback path
- `app.js` is the authoritative entry point; `routes/dashboard.js` is a legacy parallel file that should align to `app.js` patterns
